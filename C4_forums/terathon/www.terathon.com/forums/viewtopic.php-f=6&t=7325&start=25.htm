Re: Delays with rapid-playing sources

by Eric Lengyel » 06 May 2009, 19:14

Thanks. Is there any way I can see graphics that will show me the synchronization between the sound and the gun firing? I think the problem is simply that the frame rate, the firing rate, and the sound mix rate are all on different frequencies, and no two divide each other evenly. So you end up getting periodic delays that are due to the time you play a sound just being in an unfortunate position. To fix this, we would have to implement some play scheduling functionality that starts playing a sound at exactly the right sample position in the mix buffer. The Sound::Delay() function already does this for relative start times, so we would just need one for absolute start times as well.

Re: Delays with rapid-playing sources

by Eric Lengyel » 06 May 2009, 19:43

Thanks. I don't think any sounds are being dropped. The play start times just aren't in perfect sync with the frame rate, so the interval between the sounds is a little shorter than the interval between frames on which the gun is fired. When the accumulated error gets as big as the mixing buffer size, a delay occurs as a correction. It's not really a bug, but just a natural limitation caused by the different update frequencies. We'll need a precise scheduling system to make this issue go away.

Here's an experiment you can run: change the value of kOutputBufferFrameCount in C4Sound.h to 2048 instead of 4096. Does it help?
