by Pavol Lesnak » 26 May 2009, 10:54

MachineryFrank wrote:Just a question: The bones are the same in every LOD stage. Will the reduced number of skinned vertices boost performance that much?


I hope, yes. It should be logical according this: (I've been looking for some english written paper about it, it's better than putting my thoughts )

Skinning moves the model’s polygonal mesh to the correct animated relative position. Each vertex is first transformed from the mesh’s reference position to the bone’s reference position. Then the vertex is moved to its final position using the bone’s transform. If the vertex is influenced by multiple bones, each bone's influence is calculated independently and then blended together, possibly with different weights for each bone, to determine the final vertex position. Skinning may be performed in a vertex shader on the GPU (referred to here as "GPU-based skeletal animation"), or on the CPU (referred to here as "CPU-based skeletal animation").

Because skinning calculations for each vertex can be performed independently, GPU-based-skeletal-animation can take advantage of the high throughput of modern GPUs. For middle- to high-end GPUs, skinning is faster and requires less memory than CPU-based implementations. However, for some applications it may be beneficial to perform skinning on the CPU [1]. Performing skinning on the CPU improves compatibility across a wide range of systems. Older systems may have graphics cards that do not support the necessary features to perf orm skinning on the GPU. Graphics cards that do allow skinning on the GPU may have limitations that force large skeletal models to be subdivided into multiple meshes, which reduces efficiency.


Here's full araticle: http://software.intel.com/en-us/article ... animation/

Full paper also explains pros and cons of GPU and CPU skinning, both makes sense . I hope, this paper is not too far from Eric's implementation (so it will not provide misinterpreted details).

MachineryFrank - the skinning should roughly be verticess x bones x number of weights per vertex. So if you cut vertices in half you double performance. If you cut all three in half you get 8 times faster performance.

I guess it depends on performance, though, but now that it uses all the CPUs I am not too worried.

Re: Hardware skinning

by Eric Lengyel » 26 May 2009, 15:36

lazarus wrote:the skinning should roughly be verticess x bones x number of weights per vertex.


Not really. The skinning cost is computed like this:

cost = weight cost * vertex count * avg weights per vertex + bone cost * bone count

Reducing the bone count does not help very much compared to reducing the vertex count.

Well, it's kind of insulting to assume he doesn't know the basics of multithreaded programming when he's obviously done quite a lot of programming and has a lot of education.

There's already multithreaded support in the code for skinning anyway , so it's kind of a moot point. You also do not really need to break down the skinning code of one job into many threads, either though again this is already dobe. You won't necessarily even get any benefit from this at all, and it could even make it slower - especially if you don't use pthreads/hyperthreads in your threading implementation (which C4 doesn't) but heavyweight threads instead. It's not an issue of one character taking a long time but of a having lots and lots of characters that causes issues.

Aside from possibly putting the code on the GPU the biggest next improvement would probably be some kind of result caching. That way, if you are skinning the same character over and over you will get much faster results. But at the same time beware that if you are testing with one character on an engine you might be in for an unpleasant surprise when you try 50 unique characters instead of 50 of the same one.

For GPU the problems are 1) differences between ATI and nvidea hardware and drivers. The nice thing about code on the CPU is that it ACTUALLY WORKS. You can never make that assumption with video cards, especially ATI garbage. 2) If you need the info on the CPU it is not helping you because you have to go back and forth anyway. 3) You get into artificial limits like 60 bones and 4 weights. You are doing something wrong if you have more than 4 weights but 60 bones is pretty light for today let alone 5 years from now.

Re: Hardware skinning

by jwatte » 21 Nov 2009, 00:41

Back in the day, when we developed a SSE1 skinned mesh pipeline, we made LOD 0 draw with 4 weights, LOD 1 2 weights and LOD 2 1 weight. However, the difference wasn't that noticeable. There was a little difference between 4/4/4 and 4/2/2, but pretty much none between 4/2/2 and 4/2/1. (Of course, the fact that there are so few verts in LOD 2 also made the difference less).

You can also decide to skin the normal/tangent basis with a single bone (the first/most influential) while skinning position with more, as an intermediate step. That removes the need to blend two times four matrices per vertex down to one times four plus one.

However, with proper SSE implementation, the absolutely biggest gain is simply reducing the number of vertices. It's by far the biggest cunk of memory, and thus the biggest load on the caching/streaming memory subsystem, so anything you can do there is likely to help (including packing them into shorts and unpacking to floats, if you have instruction support for it).
