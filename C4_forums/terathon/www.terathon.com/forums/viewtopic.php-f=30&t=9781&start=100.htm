There won't be any graphics or other options windows until some time after 2.2 has been released. I already have my work cut out for me to update what's there. However.. you can easily enable any supported resolution of your card in full screen, or multisampling, anisotropy, whatever.. by opening your variables.cfg file in Roaming/Wingball and changing things there.

Windows 7: C:\Users\<user>\AppData\Roaming\Wingball\variables.cfg
Windows XP: C:\Documents and Settings\<user>\Application Data\Wingball\variables.cfg

Resolution: $displayHeight and $displayWidth
Full Screen: set $displayFull to 1
Multisampling: $displaySamples
Anisotropy: $textureAnisotropy

..and whatever else you want to mess with

by Adam Golden » 05 Oct 2010, 04:04

3ShirtlessMen wrote:Sorry for the loaded question. I'm interested in any particular snags along the way - things that you thought would be difficult, but turned out easy, things like that.

The biggest snag initially was C++. I have a strong background in programming, both as a hobby and professionally, but the only experience with the language I had was some basic tutorials on the web about variables, how you declare a function and some basic stuff like that which I had read back in 2005 (at which point I'd given up on the idea lol). I always wanted to learn it because I knew that most games were written with it, that it had amazing performance.. but it felt too difficult to get anything done compared with other languages I was working with. Eric has pretty much been my teacher in the sense that almost everything I know about C++ I learned from his code and searching the web to understand something when I couldn't. I won't bother with specific problems I had learning the language, because that's not really what you're asking .

One of the things I use often for work are tweens/easing equations, so a problem for me was not having these available. You can see the use of them all over this game... the intro to the level with the title and countdown, the wings sliding out, time/audio bending like that, etc.. That was more easily solved than expected by porting over the code by Robert Penner (who now works for Adobe). Once I had that in a Tweens class, the next thing I spent time on was a "Morphs" class to handle the processing and blending of tween operations submitted to it (so that several weighted inputs could influence the same output, and the weighting itself could also be tweened), which was quite complex by the time it was working well.

Terrain was a big issue because I wanted to do it a certain way (interacting with the surface, being seamless), and since I couldn't figure out how to make that work with voxels - which are still way beyond my level of understanding - I had to do it from scratch with heightmaps. I spent a long time (months?) trying different approaches, writing the tools to generate it and code to make use of it in the game. Not to mention getting the shader to handle what I wanted from it (but the shader editor is fun to work with). I just had specific ideas in mind that required a lot of custom work, so the real snag in this case was getting it all done and working.

Leaderboards. That's why I wrote C4cURL (although I regretted the naming afterwords, because it could be mistaken for a part of C4, which wasn't the intent... and I'm sure Eric would have done a better job with it in that case). It didn't take long to get together (a few days for the first version), but I really didn't want to use any external libraries... I'd rather have kept everything portable. I chose cURL because it's free and available for Mac too, but if I ever had the chance to make a finished version of this game for PS3, I'd need to do that work again with C4 networking.. well, I'm not really worried about that - Sony developer approval is like stardust, and I'll probably never have enough money to spare for a PS3 devkit and a Pro C4 license anyway. I have to struggle to pay my bills, have something left over for myself and then still have time left for this stuff after all that.. just like everyone else (well, almost everyone else).

Overall, it's been a great ride so far and I'm happy with my choice of engine. I've learned a lot, this community is great to be a part of, and I can't imagine anywhere else having the level of support we have here (from Eric and other members). I think a lot of people start out with the expectation that they won't have to work very hard to build a game... but consider that a big studio can have 50+ people working for years on a title. It's just a reality that an independent developer can't do something like that on their own, especially with no budget. I've paid for everything out of my own pocket, I've pissed off family and friends, I've even had to go without beer at times, and my game will never be a AAA title, but I'm damn sure gonna try for an A

Re: Wingball 0.5.2 Released

by Adam Golden » 05 Oct 2010, 11:52

3ShirtlessMen wrote:Do you think you'll ever release your terrain tools, or at least showcase them? xD

I did (somewhat) showcase them back in April. You can see those control points ("dots") in the 2nd picture - the terrain is generated based on cardinal splines from those. Each patch (8x8 within a block) is a 3d curve to connect those dots, with however much detail I need for the density (i.e., prairies might only need a quad with no intermediaries, whereas deep trenches would need a higher level of detail). For Wingball I'm using a single LOD because they're just hills.. and because doing a good job of LOD transitions is a real nightmare (except maybe for Eric who's already managed that, with voxels no less lol). Any given map can be any number of blocks, and within the game, patches of the blocks can either be preloaded (in the case of this game) or streaming. I opted for preloading the map because you're moving really fast, and any hiccups degenerate the gameplay. When you're "walking" around on the map, you don't notice the streaming, but moving really fast means loading a lot of patches quickly. I wrote this part of the toolset in ActionScript 3, with a PHP/MySQL back end - running locally on WampServer. I chose to do it that way based on familiarity more than anything else - I've worked with those languages almost daily for many years.

To have a seamless map you need a seamless heightmap texture, broken up into the appropriate number of pieces, one for each block, with a single overlapping pixel (so the vertices on the edges are in the same position as the next block). I make the base texture for a 2km square terrain like the one now, as a 4k block (4096x4096) 8-bit image, offset and "clone stamp" the seams away, then offset back to normal. Then I use that as a translucent overlay while "painting" the blend textures. The shader currently uses 3, 24-bit images for blending (9 color channels). 3 of these channels mix the base textures, 3 mix and overlay the ones for the road, and on the 3rd image, i use the blue channel for darkening the result of the other blends (such as around the edge of puddles, or later around the base of buildings etc.), the red channel for environment map strength (the puddle reflections), and the green channel is reserved for future use if I need it for something else.

Once I've painted the 3 textures, I then go back to the heightmap base texture, make any final adjustments based on what I painted for the material (well, I should anyway.. this map was a quicky so I didn't really spend time refining it - just needing something to use for testing), and then the final set of 4, 4k textures are ready. The first one (heightmap layer) is then resampled at the resolution I need for the tool based on settings there, broken up into pieces and imported. The 24-bit images are then broken up into 1k (1024x1024) chunks, one of each for each block, as blend textures and imported for C4 by batch to .tex files. All this "breaking up" is done with a simple form in HTML, submitted to PHP which does it with ImageMagick. Then, for "surface interaction" such as gaining points while moving on a given material, or making ripples on water vs. dust on something else and so on, I resample those at 25% to a 256x256 .tga per block and use them as a LayoutResource for the block. In my class for the map, I can pass in any position in world space and get the block which would be under that position and the distance that position is from ground contact, and then query the block with the appropriate offset for values of any color channel at that position (using cached data from the LayoutResource).

I had considered releasing the toolset at some point... but I'm still not sure. It has taken and would take a lot of work to make it user-friendly and polished, not to mention.. I really would like to get this system working with voxels at some point. Heightmaps are very limited visually - to do overhangs and cliff faces etc. now means creating separate pieces of geometry and just placing them in the world (which will happen in the levels as the game progresses). I know most of us are independent and can't really afford to spend much for development, and honestly I couldn't release it for free, or even at a reasonable price, given the hit it's already made and would continue to make on my income by doing that. So for now at least, I'm not planning to.

By tomorrow I'll have time to keep working on this game, and while I was pondering just what's next, I thought who better to ask than the people actually playing it. So, what do you want to see in 0.5.3? A few minor things are done already (mostly for compatibility, and performance when playing at lower frame rates), but I'd like to move the visual and/or gameplay side of things ahead.

OPTION 1: Level selection and a new world to race through. In this case I'd add a level select after the profile window, and you'd have 2 worlds to choose from. Noob Hills and a tropical type with sand bars, lots of water, little islands etc. - maybe replace sheep there with parrots or something that fly from one place to another. Same gameplay, Act 1 only, but new map, terrain texturing and course layout. This would include the ramps/gliding mentioned in option 2.

OPTION 2: Finish the rough version of Noob Hills with an Act 2 and Act 3. This would actually be 2 new courses with a new map for each, but have the same terrain texturing and the same general look. I'll also be replacing palm trees with something more appropriate (probably a couple of varieties).. palm trees were actually for the tropical set of levels and are just in this level now because it's the only one and I like them. In this case I'd also add some ramps to jump and glide off to get coins in the air, as that was the plan for those levels (more airborne gameplay). There will eventually be item pickups and boosting, but that stuff won't be in 0.5.3.

OPTION 3: Add a target shooting gameplay mode. This would mean shooting as many targets as you can before time runs out. There'd also be some really hard shots there for bonus time. Points received would be based on your distance from the target and how long you spent aiming before the shot. There may also be targets shooting things at you to dodge, and getting hit would knock your wingball back and make your crosshairs shake for a second (not literally 1 second.. the exact duration will depend on how the gameplay feels when I'm testing it). Eventually the targets in this mode will be evil sprites like in Serious Sam, but for now just targets . No penalty for using bullet time, but if used for every shot you'd run out half way through.

OPTION 4: Polish up what's already there. This means 10+ types of foliage instead of 3, some new buttons for the GUI (they're all the same right now), a level selection window (as I'd need this for 0.5.4 regardless), some more animation on the elements (scores that scroll from 0 up to the value, high scores at the end quickly coming together piece by piece etc.), making the dust trail effect more realistic, adding some stuff flying around in the air (leaves, etc.) and so on.
