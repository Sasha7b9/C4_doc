Version 0.6 is now available. Here's the list of changes since 0.5.3:

- Removed processor count from bottom left of UI.
- Removed the controls diagram from the pause window.
- Changed the Menu background music.
- Changed Profile buttons to Main Menu buttons on Level Fail and Level Clear windows.
- Changed UI window design (shape, animated sparkles, interactive drop shadow).
- Changed button design and state animation.

Re: Wingball 0.6 Released

by Adam Golden » 31 Dec 2010, 21:09

A note about performance options. By default the draw distance is set to 1km, with auto-adjust enabled and set to 40fps. This means that if the framerate ever goes below 40, the draw distance will gradually decrease/increase (to a minimum of 256m) in order to maintain the target rate.

If you find your draw distance is too close, even when you've set it to be far, you can reduce the foliage density and particle settings, reduce the target framerate, or disable the auto-adjustment feature and just set "max draw distance" to the distance you want to use.

Re: Wingball 0.6 Released

by Adam Golden » 02 Jan 2011, 16:21

DeRatizator wrote:what does "particle collision radius " do ? I didn't notice much particles this could be applicable to to begin with. Is it for the future ?

It's basically the distance from the camera where certain particle effects (rain atm) are "alive" and can collide with geometry such as the terrain to make the ripples on the water where the droplets impact. It's CPU-intensive to do that very far out if the particle density is high, hence the sliders. Right now, 100% of the particles up to a maximum I've set internally will be processed, but this system will be tweaked when I start working on other effects to allow the % to be set as an option (for example 50% would mean only half of the particles will have collision), which would allow the distance to be increased relative to that. It's also processing their collision every frame right now, but that needn't be the case at all - not doing so would allow greater distances. Throwing particle processing to the Job Manager would be a great tweak as well. You can't really see droplets on puddles very far anyway... their impact should pop up a little round droplet, so there's something to see "vertically" when they hit. I've considered it before, maybe it'll make it into the next update

by Eric Lengyel » 13 Dec 2011, 21:40

Adam Golden wrote:adding a call to Stop() after a new source is added in my sound effects class to prevent them from auto-playing when preloaded


You shouldn't have to do that (and you wouldn't want to). Instead, clear the kSourceInitialPlay flag for the source object before the Source base class is preprocessed:

Code: Select all
SourceObject *object = source->GetObject();
object->SetSourceFlags(object->GetSourceFlags() & ~kSourceInitialPlay);
