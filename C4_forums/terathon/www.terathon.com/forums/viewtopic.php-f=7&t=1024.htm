Controllers + node + object or whats is a game object in C4

by DanPartelly » 20 Sep 2006, 02:48

A long time ago Eric, I asiked you what was the reson to have a composite build of a object + node + controller to implement a game object. You answered me soemthing that the advantage is that anything can become a
game object by attaching a controller.

I was sceptic , and I said this design is a bad one, starting with the fact that
you maintaine game state (physics state , as poisition in scenegraph, orientation) are also game object state, and I foreseen a lot of issues with replication with your design, and generally considered it a bad one, because it is not either property centric , nor object centric, but a weird mixup of code wrote to support a scenegraph, instead of using a scengraph

Today I wonder the same thing. You fixed C4s replication system by enforcing that every node which is modified have a controller. You even said that youll do autocontrollers so you save us the pain of ading controllers everywhere. This have a lot of unwanted side effects, most important beeing

1. Each node which is a target of a script action, must have a controller !

2. Many of the new script methods one will add , to benefit from the autoasignment mechanism WILL HAVE TO MODIFY engine code to add
to the "generic" controller a mechnaism to handle the script. Basically
your forced either:
a. modify the root of controller class hierarchy in engine
b. make some other new controlelr receiver and manually attach it on target

Neither is good. Both requires way too much work for such a simple issue
like replication.

3. The system only recognizes that a implicitly wasnt a good ideea to use
object + node + controlelr. Since I must have a controller to receive messages, I could have GAME OBJECTS in the first place which send messages between themselves , and not such weird contructs. This would save many pains your design creates. You just basically now created full game objects and enforced them but because you started with a pretty weird desing , you have them split in 3 components , which is kinda weird.

Should you go with a correct and proved design, you would had a much cleaner multiplayer working from the start of the engine, and not the system you have now, which, IMHO , is fundamentaly wrong for a game ,
especially your current way to fix the problems which plagued the design.

Other disadvantages of writting code to support a scenegraph, instead of having a scengraph to support game code are:

1. The game save mechanism is OK, but is a pain in the ass to save anything which aint a node in the world. This is basically because the same problem is present there, the code is just a simple extension of scengraph
serilzation APIs.

2. The theorethical advantage of "controllers" against full game objects
is gone now. Since this build you start to enforce full game objects

3. The scripting of c4 just went tedious and difficult, because of the ammount of the new code required to make anything working in a multiplayer game

4. There is still no clear disitinction of what and who holds gameplay state in c4. Everything can hold state

5. The materials are embedded in the world, again as a result of using a scenegraph. Materials are shared between multiple worlds, not part of a single world

I personally more and more think that C4 started like a scenegraph
and not like a game engine, and everything which ressembles a game
engine was custom tailored for the scenegraph. But prolly is just a impression, and C4 was designed as a game engine from the start

Plase clear any misunderstanding I might have in the way C4 multiplayer
was fixed and why you consider it clear when I still consider it a "hack"
because I rewrite the review I wrote about C4 and I dont want any misunderstandings regarding what will go inside the review . Also , please
tell me for the review , which are the strong points of this system , your oppinion on the negative points I outlined , so I can evaluate the trade-offs between designs, for the same purpose.

Thanks, Dan

Re: Controllers + node + object or whats is a game object i

by Eric Lengyel » 20 Sep 2006, 03:31

Let me start by saying I disagree with every single point you made above except the last one about the materials. On that point, I recognize the need to have separated material resources that are shared among worlds, and I'm planning to implement a solution to that issue. As for everything else, I'll have to be brief as to not delay the next release by writing in the forums all day.

DanPartelly wrote: 1. Each node which is a target of a script action, must have a controller !


So what. It hogs up a whopping 48 bytes of memory, and it's the way the C4 sends messages to objects in a distributable manner.

DanPartelly wrote: 2. Many of the new script methods one will add , to benefit from the autoasignment mechanism WILL HAVE TO MODIFY engine code to add
to the "generic" controller a mechnaism to handle the script. Basically
your forced either:
a. modify the root of controller class hierarchy in engine
b. make some other new controlelr receiver and manually attach it on target


Option (b) is the intended way to do it. Making one generic controller for use in your game to handle generic messages would be equivalent to modifying the base class in the engine. I think you'll find the for the vast majority of custom script methods, the target will be a node that already has some kind of custom controller attached to it, and you can just call the controller's exposed script functions. This has so strongly been the case in my experience that I'm planning to change the appearance of the script editor so that you see the function calls in the main viewport.

DanPartelly wrote:3. The system only recognizes that a implicitly wasnt a good ideea to use
object + node + controlelr. Since I must have a controller to receive messages, I could have GAME OBJECTS in the first place which send messages between themselves , and not such weird contructs. This would save many pains your design creates. You just basically now created full game objects and enforced them but because you started with a pretty weird desing , you have them split in 3 components , which is kinda weird.


It's not weird -- each type of class (node, object, and controller) has a very clear place in the engine, and there's a clear separation among the responsibilities of each. Nodes are in the scene graph. There's a many-to-one relationship between nodes and objects for instancing. A controller makes changes to a node or object.

DanPartelly wrote:Should you go with a correct and proved design, you would had a much cleaner multiplayer working from the start of the engine, and not the system you have now, which, IMHO , is fundamentaly wrong for a game ,
especially your current way to fix the problems which plagued the design.


This isn't the Q3A, Doom3, or Source engine. It's the C4 Engine. It works differently. If you think it's so bad, why are you using it? Seriously, why are you here? I'm very puzzled by your persistence on these forums when it's obvious that many fundamental design characteristics of C4 clash with your personal opinions and/or preferences.

DanPartelly wrote:1. The game save mechanism is OK, but is a pain in the ass to save anything which aint a node in the world. This is basically because the same problem is present there, the code is just a simple extension of scengraph serilzation APIs.


I don't think it's difficult to save stuff.

DanPartelly wrote:2. The theorethical advantage of "controllers" against full game objects
is gone now. Since this build you start to enforce full game objects


There is no concept of "game object" in C4. It's more general than that. Everything in a C4 world is a game object by the definitions used in other engines.

DanPartelly wrote:3. The scripting of c4 just went tedious and difficult, because of the ammount of the new code required to make anything working in a multiplayer game


Again, I don't think this is difficult.

DanPartelly wrote:4. There is still no clear disitinction of what and who holds gameplay state in c4. Everything can hold state


So? The important thing is that all state changes now go through controllers. And this allows replication in a very general manner. Game implementors have some freedom as to how they use the available functionality to suit their needs.
