Re: lots of networking questions

by Eric Lengyel » 22 Apr 2009, 15:15

TheRhinoDude wrote:- what cipher is used for packet encryption / decryption?

- assuming it is a symmetric cipher, is there a runtime generation of symmetric keys through a secure mechanism such as Diffie-Hellman Key Exchange? Or is the shared secret key simply hardcoded?

- can I disable encryption?

- can I set the key and/or IV (initialization vector) for the cipher?

- can I provide my own encrypt / decrypt routines?


The packet encryption is a simple home-grown symmetric rotation cipher. It is not meant to be very secure, but only to scramble the packet data enough to make a hacker's life difficult. It cannot be modified or disabled. You can implement your own encryption at the message level if you desire.

TheRhinoDude wrote:- what is the value of kMaxMessageSize?


It's 252, but you can increase this statically by changing one declaration.

TheRhinoDude wrote:- is there dynamic MTU / packet size determiniation (RFC 1191), or are packets always (up to) kMaxMessageSize?


Increasing the message size would not really help unless you plan on sending large messages that have to be divided up into smaller packets. The engine currently does not attempt to dynamically adjust the packet size.

TheRhinoDude wrote:- at the Network Manager level, does the protocol do anything, other than successfully decrypt the packet, to determine if the packet has not been corrupted or altered since transmission?


The Network Manager provides reliable in-order non-duplicated packet delivery and protects against attacks in various ways. There are a lot of little things going on at that level.

TheRhinoDude wrote:- same question as above, but a the Message Manager level: in particular, is message digesting or some other mechanism used to ensure that the message hasn't been tampered with?


Each message type has a Decompress() function, and that function has the option of validating the information in the packet.

TheRhinoDude wrote:- any NAT punchthrough capabilities?


No explicit support at this time.

by Eric Lengyel » 23 Apr 2009, 16:46

TheRhinoDude wrote:Does this mean even voice data via Channel class is being encrypted? This seems a bit of an overkill since each individual packet is useless by itself, and I wouldn't want to pay for the cycles to encrypt / decrypt voice.


Yes. The encryption is so fast, though, that we don't really see a reason to add logic for turning it off on a per-packet basis.

TheRhinoDude wrote:So in theory, once we have the code and tap into the one places where the symmetric key is hardcoded, an change it, and therefore no other C4 server could interroperate with mine, even if the protocol ID was sniffed?


Yes, there are a couple key values that you could easily change to make your networking completely incompatible with any other title.

TheRhinoDude wrote:
Eric Lengyel wrote:It's 252, but you can increase this statically by changing one declaration.

Increasing the message size would not really help unless you plan on sending large messages that have to be divided up into smaller packets. The engine currently does not attempt to dynamically adjust the packet size.


Channel messages don't fall under this defintion?


Yes, all network traffic falls under this definition. Voice data is heavily compressed, so 252 bytes actually represents a decent chunk of playback time.

TheRhinoDude wrote:It takes virtually no more network resources to move around a 1400 byte paket than a 70 byte packet (both usually fit into a single frame), and takes very little more server resources.


I'll have to run some experiments to measure ping time and dropped packet counts versus packet size. Regardless, changing the max packet size is as simple as changing one enum value in the engine.

TheRhinoDude wrote:Since there are no dynamically sever generated keys, is there some sort of session ID or other mechanism to prevent playback of prerecorded play sessions? In other words something happens during every Connect() which in turn drives how the data looks for the rest of that connection, so that playback attempts won't work? I don't need to know how it works, just if it's there.


Yes, it's there. The server provides a new random value to each client when a connection is made, and that value affects the binary data in all subsequent packets, so playback is impossible.

Funny you should mention that (re: ICE).

I've sent many hours this week (including all of today) evaluating ICE. I like what I see. A lot. But it's still to premature to know if we'll go with it, as I've yet to put the high level features such as IceGrid, Freeze, IcePatch, etc. through their paces. If they work as advertised, then ICE will represent a massive time saver, and they do have flexible (if expensive) licensing options.

Of course, for non-commerical use, it's free (GPL). For commercial you can get an up front license (major $$$), or use a percentage royalty-based method, yearly based, with a small up front pre-payment. They seem to be willing to negotiate on the license percentage if you aren't going to need many of the high level features, or most of the languges. For example, if you were just going to use Slice for C++ and the Core, I think they would come down quite a bit. This seems like it is negotiated on a case by case basis. At least that's the impression I got when speaking with their reps, which have been extremely courteous and helpful.

If the high level ICE features and components aren't suitable for us and won't be used, then RakNet will have more to offer for us. For example, object replication in RakNet is a lot more work to get up and running, and more code to write, but it's faster. OTOH, RakNet doens't allow you to comingle clients and servers from 6 different languages...so it very much depends on your needs. ICE is more flexible and has a ton more features, but if you don't need or can't use either because they don't fit your requirements, and if you have to build your own anyway, then it's probably better to build them on RakNet. This is not suprising of course because ICE is a general purpose network middleware, and not at all game specific (although games have successfully used it). RakNet is specifically designed with a focus on multiplayer games. They really are very different beasts. For straight multiplayer, I'd say RakNet is a no brainer. But if you were approaching MMO complexity, then ICE adds a LOT of features that could save massive amounts of effort.

As such, so far I've been concentrating on the core features such as Slice and how efficient the network protocol is. RakNet has a small bue measurable advantage in the areas of control and speed, but not in terms of language support, available features, and licensing flexibility.

One potentially major issue is source code. Even with a commercial license you don't get source with ICE...unless you pay a *fortune* for a source license. That could be very important to some. But, hey if it works, it works, and you won't need the source anyway, right?

As such much of my testing this week has been around determine if we could live without the source, and so far I'm happy to say that it seems totally possible, at least for the Slice and the Core. I have yet to find a single bug, and the documentation is, as you've already seen, *fantastic*. There's no need to dig into code to see how something works. I mean the user manual is 1800 pages, and extremely well organized. Frankly, if it's a) well documented and b) bullet-proof, then for a library such as this, I don't really *need* the source code. But those are very tall orders.

ICE support *is* pricey, I won't say how much, but I will say that support for ICE for 1 developer seat for 1 year costs *more* than an entire RakNet license. Again this is not suprising, as support is how they make money with GPL. Furthermore, if you do buy a Commerical License but no Support (it's not included), then you aren't guaranteed bug fixes if any are found, and without the code, you can't fix th em yourself. This is why I've been stressing my evaluation around determining how robust and bug-free the software appears to be, as I know I *definately* can't afford the source, and will unlikely want to budget for the Support until close to shipping.

I think it's going to really come down to the high level features of ICE. If I can use them, it's going to shave many man months off of my development, and will be worth the effort and I can then live with the areas where it doesn't quite stack up well with RakNet. If I can't use them and I have to build the high level features anyway, then ICE provides virtually no advantage other than language independence, which in my case is a non-issue as everything has to be C++ anyway.

In another week or so once I finish my evaluation I'll add more to the thread. But so far I'm cautiously optimistic.

Re: lots of networking questions

by Eric Lengyel » 28 Jul 2009, 12:38

jonathono wrote:SendInitialStateMessages(Player * player) const
- Is called on the Server after kPlayerInitialized event has been received by ServerApplication::HandlePlayerEvent and before the message journal is transmitted. (Is this called for each controller server-side automatically? Or do I have to loop through the registered controllers and call it myself?)


Yes, the SendInitialStateMessages() function is called automatically on the server for each controller in the world. You don't have to iterate through the controllers and call this function yourself.

jonathono wrote:I wouldn't send any journaled messages through this function server-side would I?


No, you wouldn't want to send any messages that get journaled, nor would you want to send any state that would be updated by messages already in the journal (but it wouldn't really hurt for any more reason than making the connection process take longer).

jonathono wrote:1. Do I need to use a StateSender (Does the WorldMgr install it without my intervention, or do I have to install it (MessageMgr::InstallStateSender()) or subclass it in any way?) to send the initial state? Does the StateSender call SendInitialStateMessages()?


The World Manager creates one state sender and installs it automatically. This particular state sender is the one that iterates through all of the controllers and calls SendInitialStateMessages() for each one.

jonathono wrote:2. Is an installed StateSender function called before SendInitialStateMessages() is? As it says on the API: "it is called immediately after the Message Manager sends a kPlayerInitialized event."


The state senders are invoked in order of installation. Since the World Manager's state sender is always installed first, it gets called first, so SendInitialStateMessages() will get called for all controllers before any other state senders you've installed are called.

jonathono wrote:3. Do the controllers require or own a journaled message list at all?


There is only one journal, and it is owned by the Message Manager. (Each controller also has a list of the journaled messages that it sent, but it doesn't own them any more.) The only way you use the journal is by calling the MessageMgr::SendMessageJournal() function to send messages. There is no requirement that you ever send messages that get journaled.

jonathono wrote:4. Based on this comment in the API: "The World Manager installs a state-sending function that sends initial controller state messages to a new client. A controller can send initial game state messages by overriding the [i]Controller::SendInitialStateMessages() function."[/i] does that mean that a state-sending function is already installed without any intervention from me? And provided I have overridden the SendInitialStateMessages() function for our controller sub-class it should automatically call it?


Yep, as described above.

jonathono wrote:5. At what point would I call SendMessageJournal() on the Server?


You call this function when you want the message to be recorded in the global message journal. This helps keep track of state changes inside all of the controllers, and it provides a way for the engine to automatically transmit those changes to new clients when they join a game. An important mechanism for keeping the journal size small is implementing the OverridesMessage() function for your messages. This lets you tell the Message Manager that a new message should replace an old message concerning the same state in the journal. For example, if a message said "turn on a light", and a later message said "turn off a light", then the second message should override the first so that the first message will be deleted from the journal.
