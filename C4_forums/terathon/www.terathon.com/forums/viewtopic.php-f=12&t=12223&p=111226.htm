by jwatte » 21 Sep 2012, 21:24

Eric Lengyel wrote:Fortunately, the Intel hardware is getting much better in terms of performance in the latest generation (Ivy Bridge). But the drivers are still so terrible that Intel hardware is completely unusable for games.


Actually, for Direct3D, it mostly works. The reason for this is that Windows Aero won't work without that support, and Microsoft does most of the hard work for them.

The built-in "HD 3000" graphics has 12 "shader model 4.1" execution units clocked at roughly 1 GHz. This is more shader power than the NVIDIA GeForce 6800 had! By comparison, the NVIDIA GTX 660 (a $200 graphics card) has 960 shader units, and 144 GB/s of dedicated memory bandwidth.
However, the graphics core shares the L3 cache with the CPU. It also shares memory bandwidth with the CPU. Thus, the actual performance will still be worse than a similar dedicated graphics card, assuming the drivers work efficiently.

When it comes to frame rate, assuming the drivers work right, then you can typically get Intel Integrated graphics to run better by using the smallest possible resolution (typically 640x480.)

by MACK » 22 Sep 2012, 17:06

Yes.

There are many things you can do to reduce the overall GPU requirements.

1. The fewer Lights the better.
2. Use smaller textures, and fewer textures.
3. If possible use instances of models instead of unique models. For example, if you have 100 boxes, you don't want to use 100 hand placed original boxes, you want to use 100 instances of the same model.
4. Wise use of portals and zones
5. Non-complex shaders
6. Avoid High Poly Models, optimize your LOD
7. Avoid multiple characters with AI , and multiple objects with physics as this will affect your FPS.

(There's more I am sure, but thats a good start)

Re: About Integrated Intel Graphics

by jwatte » 26 Sep 2012, 20:54

It's also important to make sure all your textures have MIP maps.

Also, there are four major cost bottlenecks for graphics:

1) Vertex processing.
2) Pixel ("fragment") processing.
3) Memory bandwidth.
4) CPU cost of feeding the card.

If any one of those is being over-taxed, the frame rate will be low.
The above suggestions help for different bottlenecks:

Making the output window smaller (in pixels) or making the full-screen display of lower resolution (again, in pixels,) helps a lot with the pixel processing (fewer pixels to process) as well as with memory bandwidth.

Using MIP maps for all textures helps with memory bandwidth, and even more so the smaller your output window / resolution is.

Using lower-poly geometry helps with vertex processing. If you are animating skinned characters, it also helps with CPU cost.

Using fewer lights helps with both vertex and pixel processing, and possibly with memory bandwidth.

Reducing overdraw will help with vertex processing, memory bandwidth, and pixel processing. (Good use of zones/portals will do this)

Often, it's important to isolate which particular bottleneck you're seeing. You can do this by, for example, making the window really tiny (100x60 pixels) to see if pixel processing is a limitation. If the frame rate doesn't go up, then you are suffering from CPU cost or vertex processing cost. Similarly, you can replace each object with a bounding box that uses the same material/s and takes up about the same amount of size on the screen. This will let you know whether you are vertex processing bound.

Also, on different graphics cards, you will find that the balance between bottlenecks shifts. Integrated graphics are typically very constrained on memory bandwidth, and often on pixel processing. Cheap stand-alone cards are often bottle-necked mainly on memory bandwidth. High-end cards may run faster than your CPU can feed them, and thus are bottle-necked on CPU.

(There are more bottlenecks -- bus bandwidth, readback stalls, dispatcher overhead, thread switching, early-Z disabling operations,
the list goes on and on -- but the top four are the ones that almost always are where the real limitations are at.)

mulfycrowh wrote:In a game what makes the graphics running at full power ?


Has others have said that is a very ambiguous question. The full power of a game depends on the options that you has a developer give to it, the number of shaders, the number and resolution of textures, the amount of polys, the number of dynamic shadow casting lights and objects, the type and complexity of the AI, the number of skinned and animated characters, the amount of post processing effects, and on, and on, but the most important thing is how many of this options you allow in a single frame.

Now IMO if you want to make a game on C4 capable running at acceptable frames on a Intel GPU, you will need to make some serious concessions, and for obvious reasons, i don't know how much the C4 engine can scale back.
The C4 engine is a real time lighting engine there's no inhouse support for lightmapps, you can of course import lightmapps from a 3D app like Modo/Maya/3Dmax, etc, but the dynamic objects in the game including characters will not take that lightmap into account, so they will not "know" if they are on a lighted place or on a shadow, and imo for a game supporting intel GPU's you would be better served with static lights or in the max a single shadow casting light enabled per scene (just like Amnesia).

For last, has a licensee of the engine source you could in theory make the necessary changes for it to support what you need.
