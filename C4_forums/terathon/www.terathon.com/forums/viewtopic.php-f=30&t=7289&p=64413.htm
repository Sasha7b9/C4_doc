monotonic wrote:I've added a profile for the executable to my firewall to allow it to get through but it keeps telling me that it cannot connect to the server.

Any ideas?

There is one problem with the server. I've almost fixed it but not completely.
In one of our old clients builds there was on missing thing. When client starts it asks for a name. But if the user presses "Cancel" button the game quits. The "quiting" was done like:
Code: Select all
  if (dialog->GetDialogStatus() == kDialogCancel)
  {
    TheEngine->Quit();
  }

  TheGame->currentNet->JoinCommand(TheEngine->GetVariable("server")->GetValue());

I forgot, that when calling Quit() the engine doesnt quit immediately and client manages to connect. But after that the game quits. On the server i log every connect/disconnect/timeout event. So after pressing "Cancel" the client starts connecting to the server but quits immediately and the server could catch it. At least there are no log events of this. But the connection was established somewhere in the engine and the timout happens. But considering that connection wasn't established correctly, when reaching HandlePlayerEvent (that's where the connections and disconnections are loged) the player instance is not empty but i can't cast it to my GamePlayer class and when calling something like gamePlayer->MyFunction() the server crashes. Even anything like
if (gamePlayer)
{
LogHere
}
cant help here. Perhaps HandlePlayerEvent isn't the best place to log connections and disconnections. Ofcource i have ConstructPlayer overrided.
Anyway, this was somehow fixed in other builds of the client. Just added return right after Quit(). But it appeared, that some testers had that old version and that's the reason why server had crashed today.
Sorry for this inconvience again.
