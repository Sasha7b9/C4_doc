Is C4 good for TBS games?

by Avilyn23 » 19 Jun 2014, 22:31

I'm looking seriously at C4 for a turn based strategy game I'm developing. I'm not finding a lot of clear indication if that is a good fit though, since most of the examples and discussions seem to be around stunning 3D graphics.

My game has the following engine needs:
- Performant, heavy background AI processing (that doesn't degrade performance for the user, think AIs determining their moves while the players determine theirs as well)
- Performant end of turn processing
- Large numbers of objects drawn in 3D at a small scale
- Some complex,replayable non-interactive scenes with pre-calculated data

Can anyone speak to C4's strengths and weaknesses in these areas?
Does anyone know of any example TBS games that use this engine?

I appreciate the help and expertise.

Re: Is C4 good for TBS games?

by Davaris » 20 Jun 2014, 00:31

I like RPGs like Fallout 1 myself, but if I was into strategies, I would definitely do that with C4.

The engine has likely the cleanest code base there is for 3D engine, builds fast and runs fast. Fast is important, because you won't get complaints about your games failing to work, or overheating lower end machines, like one company I'm not allowed to name here.

Check out the bio of the guy that made the engine. This should give you an idea of the quality to expect.
http://www.terathon.com/lengyel/

Of course you will have to code the AI yourself, as the AI is the game. And if you want tons of critters, no problem, but they will have to be low poly.

What is your experience as a programmer? Is the movement in your game based on a grid? If so, you will have to code your own path finder, because that kind of path finding is not commonly used. What are your plans regarding networking? Single player or multiplayer? Networking over the internet is no easy task, so you should ask about that. TB networking is likely a no brainer, compared to RT though.

I hate choppy performance and optimizing is easy for me, though. With an overhead game usually people care a lot less than a FPS so it should not be a huge issue.

Thank you all for the great thoughts. Let me explain my project in a little bit more detail.

I'm building a 4X space game. It will also have a large simulation component. Think Civilization meets SimCity in space.

Turns will involve adding a set of actions to a queue to be processed between turns. This makes multi-threading of AIs a non-issue; the game world is essentially paused while everyone "thinks." Since no actions happen immediately, battles will consist of setting a variety of tactics for your ships (think Dragon Age) and then the battle will be simulated. The battles can then be "played back" once the next turn starts.

Davaris wrote:What is your experience as a programmer?


I think there are two important factors at work here - 1.) is C4 a good engine for me and 2.) is C4 a good engine for developing a Turn-Based game. If the second it true, then the first can become true through learning and experience.

I'm a professional full-stack web developer. I deal mostly with Ruby, JavaScript, SQL, and Java. I also have a fair amount of C++ AI programming experience gained from hobbies (mostly building ASCII based AIs for well-known board games, think command line Chess). I have academic experience with OpenGL. I obviously expect to have significant learning curve in this space, but don't don't want that potential challenge to steer me away from using the best tools available. Using bad tools is more of a deterrent for me than lack of knowledge in the problem space. I'm not afraid to refactor.

Davaris wrote:Is the movement in your game based on a grid? If so, you will have to code your own path finder, because that kind of path finding is not commonly used.


The game will use a 3D coordinate system. Since space is large, it can be assumed that objects always move in a straight line without collisions from start to destination. The challenging part will be users specifying arbitrary points in 3D space. Does C4 have good handling for that? It's good enough if it can detect the 2D coordinates relative to a plane from a click. I can build out the rest.

Battles are a bit different. They don't need to handle user interaction, but do need to handle things like acceleration (both changing speed and changing direction) and collisions. I'm expecting that to just be math, but if C4 has built in patterns for handling that sort of thing, even better.

Davaris wrote:What are your plans regarding networking? Single player or multiplayer? Networking over the internet is no easy task, so you should ask about that. TB networking is likely a no brainer, compared to RT though.


The reading I've done about C4 convinced me it had what I needed for multiplayer. I need to understand both UPD and the game engine better before finalizing design. If I had to blurt something now, I'd say it will likely will consist of the host processing the end turn and synchronizing data to the other clients. A model where each client processes the turn and just verifies the result is also interesting (especially from a prevent-host-from-cheating perspective), but I have concerns about synchronizing the random number generators across architectures. That's another case where if C4 handles it, great; if not, I'll figure something out.

I've been planning on using multiple, nested coordinate systems, but I don't know if the engine will support that. Stars would all share a coordinate system. When "at" a Star, a different coordinate system would be used to mark where each planet is. When "at" a planet (still also "at" the star), yet another coordinate system would be used to mark any moons, satellites, etc. When rendering any specific scene, you realistically would only see objects at that level anyway.

The biggest pro to that approach is being able to use plain old integers for storage while still having very granular coordinate system. The cons probably depend heavily on the capabilities of the game engine.
