General Development Philosophy With C4?

by DrVonBraun » 05 Jul 2012, 17:31

I got my license yesterday and have spend my time since then working through the tutorials and going step by step on a roadmap I drew up to learn what I need in order to be able to transfer my client server based code from Ogre to C4. The more I read the Wiki and Docus the more I am beginning to think that there is a general difference in design philosophy when comparing my raw Approach to C4. I want to figure out if I am right there since it would change parts of my design and, as I understand it, would make my life easier. Here are my thoughts:

In my current code I am using Ogre as a very low level interface to DX9. Basically I am using their GFX card initialization, their scene graph with extensions, their animation system and their resource loader and thats it. Everything else, all objects, meshes etc are made by me creating DX hardware buffers and thus creating render objects the old fashion way.

Now to get a scene or world, I edit it in 3DS by placing lots of props there, adding additional information, like invisible floor triangles that define walkable surfaces, place invisible boxes that mark for instance resource spawning points etc. Then I run the OgreMax exporter. The next step is to run various converters I wrote, for example my world converter reads the exported scene, creates static geometry by extracting objects in a 40*40*40 meter grid and matching triangles with up to 16 textures into one object so that they can be sent as one render batch. The converter also extracts all the extra info like floor triangles, spawning points, special boxes etc and creates data for the server from it.

Then, my server runs on that spartanic data, determines height values, checks if a character can stand on a certain spot, determines when a move runs out of supporting surfaces to halt the character, calculates collisions based on bounding boxes etc. The client on the other hand has the full graphics data for render purposes.

My point is, that I explicitly have to tell the server certain info by placing special items in the scene and so I am designing two worlds, one for the server and one for the client.

I'm getting the feeling from my learning experiences that C4 uses a different approach in which everything is integrated. The world editor seems to offer an awful lot of ways of storing information about nodes, geometries etc which are useful for the client or the server or both. So I am thinking that maybe it is not necessary for me to have these separately programmed code sections on the server that do all the coarse estimates about collisions, positioning etc but I'll be able to use C4 on the server as well (I understand the server mode is broken in the current release but it will be fixed for the next release which is why I wasn't able to try it out yet).

So my question is: Am I on the right track there? Is C4 meant to and capable of also providing code for the server side of a MPOG? Can I do position determination, character movement and all the stuff one can easily do in a single player game on the only machine involved on a C4 server implementation? And, provided the server mode worked in the past and is only temporarily broken, how is the experience with it speedwise? My server code's primary goal is speed and I am willing to sacrifice some exactness there so that I can accommodate as many characters as possible. How is the C4 server mode with regard to speed?

If it is usable in practice, I wouldn't mind replacing my code (which isn't finished yet) with the C4 server mode, especially if it saves me work.

Thanks

Re: General Development Philosophy With C4?

by jwatte » 05 Jul 2012, 23:20

Fratercide wrote:The one concern I recall (other than the learning curve) is regarding the lack of predictive features in movement as any lag caused excessive warping.


C4 has one particular approach to the networking puzzle. There are many different parameters, including (but not limited to):
- Do I send state snapshots, or just inputs?
- Do I move the client ahead of the server, or show control lag for the client?
- Do I display remote entities?
- What level of resolution do I need for different kinds of entities?
- Do I display different things to different players?
- What pieces of data do I give the client control over?
- How precise do I want shared rigid body simulation to be?
- Do I run server hit detection, and if so, using world state as-is on server receipt, or as-were on client send, or something else?

For an "M"MPOG (where "M" stands for "Massive,") the choices made by the C4 demo game and default implementation probably aren't optimal. For an FPS that's played on a LAN, C4 does very well. For an FPS played over very long distances, the feeling of the demo game is different than for other games, such as CoD or MW or Planetside (each of which has a different approach.) If you want to emulate the feeling of one particular game, then you have to design the networking the same as that game. (In 2009, I played the then-demo game against a guy in Finland -- it worked alright, but wasn't Unreal Tournament type snappy)

It is also totally OK to use C4 as a scene graph, and add a Controller to each scene node that just takes position/orientation information from a totally separate physics and networking system. That's a totally sane thing to do, and will give you wider options of trade-offs along the many different axes of networked game implementation than using the default, built-in networking will do.

If your question is about C4, ask here. If your question is about networking in general, then you might want to try something like the networking & multiplayer forum at http://www.gamedev.net: http://www.gamedev.net/forum/15-multiplayer-and-network-programming/.

by TheRhinoDude » 06 Jul 2012, 09:08

jwatte wrote:It is also totally OK to use C4 as a scene graph, and add a Controller to each scene node that just takes position/orientation information from a totally separate physics and networking system. That's a totally sane thing to do, and will give you wider options of trade-offs along the many different axes of networked game implementation than using the default, built-in networking will do.


This is exactly how I use C4. I think for a MPOG / MMOG that has significant parts already built, that would be a very logical way to use C4. In your case, you've already built much of your infrastructure around Ogre, and Ogre was basically just a rendering engine. You could either retool everything to be built around the way C4 does things, or you could use C4 as an Ogre replacement. Both are viable approaches, but the later might get you up and running quicker. But I think you need to play around with C4 a lot more than a day or two to make your decision.

As has been noted, C4 demo work very well for LAN environments. But keep in mind that C4 Networking does not have to be used as it is in the C4 demo. There are several levels to the networking functionality and you don't have to use the highest level. Plus as Jon pointed out there are tons of options to choose between. You are not limited to using it in the way that the Demo uses it. What Jon said is very true, the networking in C4 Demo it is heavily skewed towards LAN party type gaming, but that doesn't mean your game has to use it this way. There are very low level networking API's exposed that would allow you built any type of networked game.

Specifically speaking to prediction, if you look at the C4 architecture, this is not something you would expect to be in engine itself as it is hard to do generically; it is too game specific. It should be in the game. If you need it, just add it to your game. Everything you need to support it is there.

Don't get me wrong, someday I hope prediction is added to the demo game. But frankly, when you start your game you shouldn't be using the demo as a starting point. You should be starting with a fresh project. Still, I'd like to see this if for no other reason so that people stop consideing C4's networking to be deficient just because what plays well over the LAN doesn't play well at Internet latencies. Frankly, the demo isn't designed to do that, so it's no wonder that it doesn't play as well. But just because the demo doesn't tacklet this doesn't mean your game can't.

Also, in all honesty, I haven't seriously tested C4's demo networking since 2.6. It may be much better now. But it sounds like client prediction isn't in there yet.
