Re: Dividing in shader editor

by Eric Lengyel » 14 May 2010, 16:34

On some/most/all graphics hardware, there is less silicon available for division than there is for multiplication. For example, the hardware might be able to perform two multiplications per cycle, but only one division. Thus, using multiplication instead of division, where possible, leads to better instruction scheduling.

In the tip under the Divide process, I didn't mean that you should create Reciprocal processes instead. I meant that if the input is constant, then you should work out its reciprocal by hand and use that as the input to a multiplication instead of dividing by it. Now, you've said that the value of the input can change, so it is not a constant even though the name of the process is Constant Vector. In that case, you should just use the Divide process.

Re: Dividing in shader editor

by Eric Lengyel » 15 May 2010, 02:59

Yep, that's the bug. Early versions of the GL_ARB_fragment_program extension specification had a broken grammar rule in their program syntax that erroneously made it illegal to have constants like "1.0" in a fragment program. Instead, if you followed the grammar precisely, you would be required to write "{1.0}.x" instead. This issue was fixed in revision 13 of the specification on 8/14/2002. Nvidia had always implemented the correct behavior that would allow "1.0" to be legal because they have intelligent engineers who implemented what was intended by the specification instead of what was actually written in the specification. But ATI employs a big group of idiots who just decided to implement exactly what the specification said even though it was clearly wrong. When the specification was fixed, ATI didn't bother to fix their compiler, and that was almost 8 years ago.

I had originally implemented a workaround in the C4 code generator for the scalar process, but didn't do the same for the case that a single component of a vector process was used. Version 2.0 now includes workarounds for both processes so that the ATI compiler doesn't fail.

This is actually working correctly. The value of B in a division process is always a scalar (that's how the hardware works), so it takes the first component if there's a vector input. Just change the swizzle to w instead of zwww. You should also change the A input's swizzle to just y, and then remove the swizzle from the division's output.
