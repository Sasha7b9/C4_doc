Re: BTR - December 2008 promo.

by rijkaard » 19 Dec 2008, 16:58

DeRatizator wrote:
But what if it is moving, or beginning of each animations has a bit different starting frame ? For instance VoH has lots of problems with blending because of that.


That's exactly the same problem we have.
One of the Three problems that we have.

The first one it's not a programming issue, but a known transition problem for very different beginning and ending frames. When frames are similar problem is not present, Havok Animation blending is perfect and very modular.
Because, as i said before, some animations ( e.g.: idle/combat idle ) were done by hand, some other, ( e.g. : running or spin kick ) were done adapting some mocap .bip, everything in short time with no common initial starting frames.
In the rare cases where we have similar ( if not equal ) ending and starting frames ( e.g.: transitions beween some round , circular or tornado kicks ) results are perfect.

The second problem it's that i experimented that animations ( like every other aspect of a game ) needs tuning too. Because if you see something running ok inside MAX it's not obvious that it will be ok running ingame, especially regarding playback speed.
In this stage things ( independently from the fact if the content is good or not ) need still alot of tuning.
We need to tweak configuration files as to have for every single animation different ( even slightly ) playback speed and ease in and ease out time.
I tested it only with running animation, for example, and i had extremely different ingame effects with only playing with 3 values: ease in, ease out, playback speed.
But tweaking, as you know, costs TIME.
And, with limited human and financial resources, i prefer FAR more to add new features and stabilizing the existing ones, rather than doing things that probably have to be re-done when new assets will enter and completely substitiute the old ones..

The last, and maybe the WORST problem is that, nowadays, for a nextgen title character, there are TONS of animations realized by squads of guys. e.g. Solid Snake of MGS4 has 4000 ( four thousands ) animations.
Every character of our video have less than 20 animations total in number.
If they seem more it's only due to ragdoll blending technology.
This can led to several problems, the most important one is character sliding, because in several occasions simply there is NOT the right animation to play ( typical case: hit recieved and character pushed back: we have no go back animation ), and the blending cn't save your life everytime.

My advice for you, for your project, if you don't have ( i suppose not ) resources for build more than 50-100 animation for character, but you have the time to tune, is to try to tweak the easeIn/easeOut time, before re-doing animation content and see if results are better. I don't use C4 blending animore, but i think to remember that you could play with the same parameters too, even if i don't remember their name...

You need to make sure the first and last cycle fit together right but it should be easy to spot and correct..


We were not talking about animation cycles. But about the transition ( blended or not ) between 2 different animations A and B where A end frame differs significantly from B start frame.

bryced wrote: If you have foot speed that doesn't match the ground speed it's mainly a programming issue (though obviously you might need to adjust the actual animation too if it's really off). That's what I thought was being pointed out (and what I noticed).


I have character controller capsule perfectly driven by the real animation speed. I obtain this easily because i use the "extract motion" feature of havok animation for calculating character speeds during all move/hit/attack/jump etc. If run animation goes at 6m/s inside the game then character controller runs at 6m/s.
This has been intensively tested and confirmed.

The slide effect that sometimes occurs is generated, as i previously said, when you have an event but you don't have the correct animation to handle it ( e.g. character pushed backward and don't have walk backward animation, little step forward or backward and we don't have little/single step animation yet... etc.. ) then character seem to slide but, instead, the character controller is simply moving without the proper animation to play in that moment.
And it's a known bug. ( we call it bug, even if it derives from the lack of content )
We currently need backward animation, strafe left, strafe right, being pulled fw, backw, spin around z axis , stop/start motion, single step fw/backw. And this just for simple movements. Lacks in complex movements and attacks and combo are even bigger.

Honestly, i would not say that something depends from code for any application or demo i would eventually see on screen, without reading the code first.
Neither if i would be a master in that particular API or SDK ( and i don't think this is the case ).
