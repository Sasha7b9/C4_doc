Re: Networked player movement in Game code

by CodeNewt » 11 Dec 2011, 22:29

Journaled messaging is probably the biggest reason. The server can't send the current movement of a player to a newly connected client if it doesn't know what the last BeginMovement or EndMovement was from the player.

There are other reasons too, such as simplifying the lag compensation model. It'd be difficult to figure out whats happening inbetween frames (and inbetween clients) when you have no server tracking a player's input.

What you CAN do is, send it to the server AND send it to itself so it can "start" the motion immediately instead of getting the lag effect you get in games like World of Warcraft (where you are running in the same spot due to lag?)

Re: Networked player movement in Game code

by Eric Lengyel » 12 Dec 2011, 02:20

One additional HUGE reason not to send information from client to client is that you can't trust client machines. We don't even let clients know the IP addresses of other clients connected to the server. Imagine a client intentionally sending bad data to another client in an attempt to crash it or as a denial of service attack.

Re: Networked player movement in Game code

by Zitheral » 16 Dec 2011, 05:46

Security is one reason not to send directly to clients... synchronization is another. Imagine the discrepancies that would arise between the clients and the server if they were all talking independently... it would be a bit of a mess. Trying to force resyncs periodically would lead to stuttering, popping, jumping, and all kinds of other yucky things.

The necessity of sending everything to the server and having to wait for a response (the current implementation in C4) is what makes multiplayer feel bad at the moment. You press a button and it takes 50-100ms to get to the server, and then 50-100ms to get back to the client. So the player is holding the button down for 100-200ms before the character on the screen starts moving. This doesn't feel good.

It is not an easy thing to implement compensation into any engine with physics because if you let the client start predicting movement, you have to keep the physics system from going bananas. Some engines like Halflife and Quake sim entities one at a time... meaning that if there is a collision (or a predicted collision) you can "go back in time" for those JUST those two entities to sort out prediction errors after the fact. As an example, imagine a player running into another player. If you are allowing the local client to predict the movement of the player to avoid the 200ms lag I mentioned above, it is possible that the local client will register a collision with another player during predicted movement only to find out later from the server that no collision really occurred. This means you have to correct the prediction error and "resim" the two players to find out where they really should have been.

I don't think you can do this in C4 because the entire scene is simmed at once. It is an all or nothing deal. A tricky problem. I keep hoping that Eric will have time to investigate a proper lag compensation system for his Demo Game but so far, he hasn't had time.

Re: Networked player movement in Game code

by CodeNewt » 16 Dec 2011, 12:10

Zitheral wrote:You press a button and it takes 50-100ms to get to the server, and then 50-100ms to get back to the client. So the player is holding the button down for 100-200ms before the character on the screen starts moving. This doesn't feel good.

But that is just personal implementation (and therefore unrelated to the C4 Engine)... You can send "to yourself" the same message to get your character moving "ahead" of time. Basically, before the server is even aware that you are moving, you start moving on your screen. Then the server will receive the message and start performing the same action. You then have the server compensate for your ping (eg if your ping is 200ms, then you give the play a 200ms boost on the server of his action to compensate, or you can go half that and then send back the adjustment to the player)

This results in a much more immediate response for the player, meanwhile the server maintains control over where you actually are.

I have not so I can't attest to the actual difficulty of this. I never said it was easy, but it is not something that really could be solved on the level of the game engine itself because each game can have a different method to handle this. Like I said, World of Warcraft doesn't have lag compensation for motion. Meaning when you experience lag, your character doesn't move because you are waiting for the server to verify what key you pressed and process what your motion will be. While a game like Counter-Strike: Source will send the message to the local player to allow immediate response. Though Source does a lot more for lag compensation about which you can read at VALVe's dev wiki. It is an interesting read though.

In any event, I'm looking for this type of implementation in the demo game so that I can see what "levers" Eric works with... from that we can adapt it to a personal implementation for our specific gametype.

AFAIK the demo game does not ship with any lag compensation, what Eric does is send snap shots to the clients to correct objects getting out of sync and let the clients calculate their own physics. This is an appropriate model, send clients the "motion" and the "direction" and let it calculate its own physics for interpolation between the "correction" packets, but it doesn't account for lag between the server and the client.

Eventually I'm going to try to tackle this problem, but right now single player games for me.

Re: Networked player movement in Game code

by Zitheral » 18 Dec 2011, 12:10

Wow definitely has lag compensation... player movement is predicted on the client side. Even using abilities is partially compensated because the client will begin to do player animations (like spell casting) even though it hasn't heard back from the server yet. That is why if you have high lag, your player will start casting animations and then freeze in the first few frames of it awaiting for the server to tell the client it is ok to finish.

I still believe it would be a very good idea to implement lag compensation into the Demo game A) so that prospective buyers do not get the false idea that C4 has bad networking support and B) so that developers have a blueprint for the best method to implement lag compensation for whatever genre they are working in.

The needs for lag compensation are surely different for an RPG vs an FPS vs a fighting game -- but the places you make your edits and the methodology for addressing each of the pieces would be very similar.
