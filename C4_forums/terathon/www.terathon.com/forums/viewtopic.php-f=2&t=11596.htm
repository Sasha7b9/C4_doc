Re: Version 2.8 Alpha Now Available

by Javier Moya » 06 Mar 2012, 16:19

ska wrote:IT´s possible to paint a paint space texture on the top of another paint space texture?
So you need to create some material? It´s not easy, as just assign a material and start to painting?


Paint spaces are not textures (or a texture stamp tool). They work more like a projected mask (perpendicular to the z axis of the paint space). This is why you need to create a shader (which I think is great because you have all the power of the shader editor). Then you can use the paint space specific processes to use this mask (or masks, 1, 2 or 4) in any way you want inside the shader. And no, you cannot use more than one paint space with the same geometry.

Robert wrote:I bet that with animated / moving paint space textures, one can have wave-ish appearing/disppearing foam so that it doesn't look so even ?


The foam looks even because the wave generation system is not active in the world editor (I wasn't refering to the texcoords animation). In any case the foam has a texcoords animation different from the current wave textures. I've added a sine process so it goes backwards and forwards a little.

Re: Version 2.8 Alpha Now Available

by Eric Lengyel » 06 Mar 2012, 16:28

Just a little clarification on the paint spaces: Each geometry can be associated with only one paint space, but each paint space can have up to four channels that can be used independently for different purposes in the shader. (It is also possible to use channels together if, for example, you just wanted to spray paint color graffiti onto a surface.) In the Hell's Mouth screenshot, a full four channels are being used on the same geometry to independently control where cracks, moss, broken concrete, and puddles are shown.

I have a few questions regarding some features in 2.8
The visibility hierarchy and transform hierarchy have been decoupled. The transform tree still exists in the same form that it always has and corresponds to the node/subnode relationships. The visibility system now uses a new DAG structure on a hierarchical grid with fixed cell sizes inside each zone. Nodes are inserted into this DAG automatically by the engine.

and
The infinite zone now has a special bounding box that is used to define the maximum extents of the visibility graph with that zone. This box should be resized in worlds with large outdoor areas in the infinite zone so that the box encloses all static nodes other than terrain and water. The default box size is 1×1×1, but the benefits of the visibility graph don't kick in until it's at least 16 m wide in either the x or y directions. Nodes outside the box will still be visible, but they won't be part of the visibility DAG. Subzones are not affected by the infinite zone's bounding box.

Eric, could you please shed some light on this? What are these for and what are the benefits of them? Just curious...
