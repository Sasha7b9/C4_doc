Considering Switching Engine, A Few Questions First

by DrVonBraun » 03 Jul 2012, 19:16

Hello all,

I am part of a very small indy team and I am responsible for programming. We have been running a very small isometrical MPOG for 7 years now and for about the same time we are working on a new game with 3D, better gameplay etc. While the server part and basically the client part are making good progress, repeatedly I ran into trouble with the 3D part. I started with Irrlicht and got some nice environment going but it was too slow and the animation part wasn't good enough. So I looked around pretty hard about 2.5 years ago and then decided for Ogre. At the time it seemed like a good choice. The technical features were pretty much in the top range, at least from the description, and my main fear about all other engines we could afford was, that they were all run by one man whereas Ogre was run by a team which, in my eyes, guaranteed continuity.

Now however, the problems are mounting up.

First of all, I'm sure many of you are aware of this, the lead programmer has left the Ogre team and that threw them into total disarray. The 1.8 version updated was a whole year late and they don't even have a public change list for that version. The roadmap for their version 1.9 and 2.0 on their forum reads like chinese to me (I'm an application developer. My 3D knowledge is basically restricted to setting up vectors and quaternions right to place scene nodes and work with triangles and 3D coordinate space). Clearly there isn't anything on their list I need.

From a technical standpoint I ran into nothing but problems as well. First, all their out of the box high level objects like entities, characters etc were too slow and too unflexible. Ogre is so exorbitantly complicated that diving into the code and changing it for my need is out of the question, not to mention there is basically zero documentation. So I ended up accessing the DX9 vertexbuffers directly and creating my own render entities. I was able to archive good enough speed and flexibility that way but it cost me weeks and months to program all that stuff which in my eyes, a 3D engine should provide in a working fashion. There are other problems as well, mainly their resource system. I'm loosing texture memory although the list of textures does not grow, yet the gfx card runs out of memory.

It is a quagmire and despite the fact that we are pretty far in our game development I am seriously considering changing to another 3D environment. The obvious choice these days, after reading reviews and comparing features, is the C4 engine. Now I would like to ask a few questions about it's features before I invest weeks in getting to know the system and transferring my code (not to mention the art pipeline). Hopefully somebody will be able to help me with these questions.


1) I'm using my own landscape rendering system because Ogre's was too complicated to use and frankly it's not too hard to program a triangle based terrain system. I understand that C4's voxel technique is far superior though. However when dealing with a client server based game, the server will necessarily have a more coarse representation of the landscape of various zones for memory and speed reasons. In my implementation I have access to the triangle information (since I edit the landscape in 3DS) and then my converter splits it up in a part for the client to render and the server to calculate height values, basically from a height map. Is it possible to gain that sort of access to the terrain info in C4 too? I'm not afraid of writing a new converter, but I would need to be able to access the terrain info (XZ/Y values) and extract them in some sort. I understand C4 stores the terrain in it's own format but is there a way to achieve what I need for the server?

2) A very big part of our game is dressing up characters with various clothes on different layers. I have a converter that preprocesses the bodies and clothes as they come from 3DS through the OgreMax exporter and I store them in my own data format, prepared to be put on the body in various layers. To do that, I must assemble a character on the fly from a skeleton and build the mesh from triangle information that include texture handles, bone bindings and 3D positions. Is it possible to do that in C4 efficiently? I'm asking that way because of bad experience in Ogre where the legitimate way is to use a ManualObject which was about 1-2 seconds per assembly whereas my later solution with DX9 hardware buffers directly was lighting fast. My point is, I wouldn't want to have to dive into the depth of DX or OpenGL programming again, I'm hoping for a high level solution that makes my live easy for a change.

3) The Ogre static geometry was extremely slow due to the fact that they didnt optimize state changes on the gfx card by grouping objects together automatically, so I ended up writing my own converter which created blocks of, say 40*40 meters and assembled them using up to 16 textures which could all be sent in one batch. How is the static geometry part in C4 in terms of performance? If I place, say a bunch of houses that use the same texture in close proximity, will each be sent as one batch or are they optimized and send in fewer batches?

4) Does the UI system (buttons, sliders etc) allow for skinning? I have a very nice skin that I use for CEGUI, which I use on top of Ogre and I would like to be able to reuse the graphics from that skin.

5) How is the general experience with the Collada export-import process for animations? Is it possible to have say multiple skeletons with the same setup with one animation each and mix them into one skeleton upon loading or is it better to have all animations in a sequence in one skeleton? I had a pretty hard time getting all this going in Ogre and frankly , I still don't understand their multilayer system of animations, animations states and animation sets. I got it working but I dont understand it, which always frightens me.

Lastly which version should I buy? Is there a real advantage to the 800$ version? How realistic is the "change request" feature in that version and how likely is it if I run into a problem that a change request will be considered as reasonable?

Sorry about the long post but I'm desperately trying to figure out whether to switch or not at this point and I'm trying to get as much information in as short a time as I can. Of course I am reading through the API documentation today but I was hoping I could get my most pressing question answered by some knowledgeable people at the same time.

Thanks

DrVonBraun wrote:1) I'm using my own landscape rendering system because Ogre's was too complicated to use and frankly it's not too hard to program a triangle based terrain system. I understand that C4's voxel technique is far superior though. However when dealing with a client server based game, the server will necessarily have a more coarse representation of the landscape of various zones for memory and speed reasons. In my implementation I have access to the triangle information (since I edit the landscape in 3DS) and then my converter splits it up in a part for the client to render and the server to calculate height values, basically from a height map. Is it possible to gain that sort of access to the terrain info in C4 too? I'm not afraid of writing a new converter, but I would need to be able to access the terrain info (XZ/Y values) and extract them in some sort. I understand C4 stores the terrain in it's own format but is there a way to achieve what I need for the server?


You can access the vertex and triangle data for any geometry in the scene, including voxel-based terrain. This information is stored in the GeometryLevel class, which represents a single level-of-detail in a complete GeometryObject.

DrVonBraun wrote:2) A very big part of our game is dressing up characters with various clothes on different layers. I have a converter that preprocesses the bodies and clothes as they come from 3DS through the OgreMax exporter and I store them in my own data format, prepared to be put on the body in various layers. To do that, I must assemble a character on the fly from a skeleton and build the mesh from triangle information that include texture handles, bone bindings and 3D positions. Is it possible to do that in C4 efficiently?


It should be possible to do this, but I don't know of it ever being done. There might be some minor difficulties such as the need to tell the engine to rebuild the vertex buffers after your new data has been put in place.

DrVonBraun wrote:3) The Ogre static geometry was extremely slow due to the fact that they didnt optimize state changes on the gfx card by grouping objects together automatically, so I ended up writing my own converter which created blocks of, say 40*40 meters and assembled them using up to 16 textures which could all be sent in one batch. How is the static geometry part in C4 in terms of performance? If I place, say a bunch of houses that use the same texture in close proximity, will each be sent as one batch or are they optimized and send in fewer batches?


When the scene is rendered, the engine automatically groups visible geometries by material and other rendering state so that state changes are minimized. In OpenGL, multiple draw calls without intervening state changes are extremely cheap, so rendering several copies of the same object doesn't cost much at all. Nevertheless, we are currently implementing an optimization that will render multiple copies of the same "instanced worlds" in a single draw call.

DrVonBraun wrote:4) Does the UI system (buttons, sliders etc) allow for skinning?


Yes, to a degree. You can replace the texture maps used by the UI system with your own, as described here:

http://www.terathon.com/wiki/index.php/ ... a_GUI_Skin

DrVonBraun wrote:5) How is the general experience with the Collada export-import process for animations? Is it possible to have say multiple skeletons with the same setup with one animation each and mix them into one skeleton upon loading or is it better to have all animations in a sequence in one skeleton?


What we usually do is import separate animations for each character. If you have a bunch of characters with exactly the same skeleton, however, you can apply the same animations to all of those characters.

DrVonBraun wrote:Lastly which version should I buy? Is there a real advantage to the 800$ version? How realistic is the "change request" feature in that version and how likely is it if I run into a problem that a change request will be considered as reasonable?


The benefits of the pro edition are listed here:

http://www.terathon.com/c4engine/professional.php

There is one more perk that we recently started as well, and that is access to development builds that are made available more frequently between major releases.

I assume that what you're calling a "change request" is what we call a "support incident". Here's a description of what a support incident means:

http://www.terathon.com/wiki/index.php/ ... _Incidents

We take support incidents very seriously, and you can always expect a solution to a problem within a matter of days (as long as the problems fits within the scope of support incidents).

In the past (a few years ago) I worked on a project with C4 where changeable clothing was also quite important to game-play. Initially there were issues, some to do with our models and some to do with the way animations worked in the C4 engine. However, with Eric's help we were able to iron out these problems. The process should now be a lot more straight-forward. At runtime you can add your clothing models as a subnode to character model (which contains a skeleton). There might be a Node flag or two that you need to fiddle with in order to get things working, namely the kNodeAnimateInhibit, but other than that it should be very straight forward. With C4 there should be no need to ever touch the OpenGL back-end. Even if you want to create custom geometry C4 has a means of doing this without having to touch the low-level 3D graphics pipeline.

EDIT: We also implemented FaceGen and were able to update the geometry (and texture materials) in real-time. So this sort of thing is definitely possible also, however it's not nearly as straight forward as simply attaching clothing.

DrVonBraun wrote:3) The Ogre static geometry was extremely slow due to the fact that they didnt optimize state changes on the gfx card by grouping objects together automatically, so I ended up writing my own converter which created blocks of, say 40*40 meters and assembled them using up to 16 textures which could all be sent in one batch. How is the static geometry part in C4 in terms of performance? If I place, say a bunch of houses that use the same texture in close proximity, will each be sent as one batch or are they optimized and send in fewer batches?

C4 does have optimisations for static geometry. The portal system (when levels are designed properly) also ensures that only visible parts of the level are pushed to the video card. I don't believe C4 uses geometry batching (as model skinning is done on the CPU), but perhaps it does for static models. Eric will obviously be able to give you a much more detailed answer. Additionally, C4 has a very nice imposter system that can be used to replace trees etc. with old-school Doom style billboards at a distance. However, the visual results are quite amazing due to extremely intelligent use of shaders (3D lighting replication by 2D textures etc.) so you can't tell the model has been swapped out for a imposter.

DrVonBraun wrote:4) Does the UI system (buttons, sliders etc) allow for skinning? I have a very nice skin that I use for CEGUI, which I use on top of Ogre and I would like to be able to reuse the graphics from that skin.

Yes. It's probably not quite as flexible as the dedicated GUI frameworks but it does the trick. C4 also has a visual user interface creation tool.

DrVonBraun wrote:5) How is the general experience with the Collada export-import process for animations? Is it possible to have say multiple skeletons with the same setup with one animation each and mix them into one skeleton upon loading or is it better to have all animations in a sequence in one skeleton? I had a pretty hard time getting all this going in Ogre and frankly , I still don't understand their multilayer system of animations, animations states and animation sets. I got it working but I dont understand it, which always frightens me.

I'm not an artist so I'm not entirely certain about the creation process. But it should be possible to export a Collada skeleton with several named animations (or sequences) attached to it (EDIT: It seems I was partially incorrect here. As Eric mentioned, although multiple animations can exist in the one modelling tool file you must export each animation separately for use within C4). You can import this and C4 will provide you with access to each of the named animations. C4 has a fantastic animation system based around the concept of an Animator.
