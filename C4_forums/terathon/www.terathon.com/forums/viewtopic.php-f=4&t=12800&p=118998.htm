by a2k » 11 Apr 2013, 16:55

There are a couple things you can do.

Drawing Custom Geometry is one.

Another, I don't have an immediate source example, but I have direct line drawing going on in my Recast demo. It's the same method that both Ludi and Davaris used for their Recast integrations. Your World::Render() overridden function becomes the entry point.

EDIT: I decided to dig it out for you

Code: Select all
   void Draw(RenderType type, const Array<Point3D>& pts, const Array<ColorRGBA>& colors, ColorRGBA alphaColor)
   {
      if (pts.GetElementCount() == 0)
         return;

      unsigned_int32 stateFlags = kRenderLineSmooth | kRenderDepthTest | kRenderDepthInhibit;
      Renderable lines(type, stateFlags);
      List<Renderable> renderList;
      List<Attribute> attributeList;

      DiffuseAttribute diffuse(K::white);
      attributeList.Append(&diffuse);
      
      if (alphaColor != K::white)
      {
         // Couldn't get the ambient pass working for alpha blend with lines
         lines.SetShaderFlags(lines.GetShaderFlags() | kShaderAmbientEffect);
         lines.SetAmbientBlendState(BlendState(kBlendSourceAlpha, kBlendOne));
      }

      lines.SetMaterialAttributeList(&attributeList);
      lines.SetVertexCount(pts.GetElementCount());
      lines.SetAttributeArray(kArrayVertex, &pts[0]);
      lines.SetAttributeArray(kArrayColor0, &colors[0]);

      renderList.Append(&lines);
      TheGraphicsMgr->DrawRenderList(&renderList);
      renderList.RemoveAll();
      attributeList.RemoveAll();
   }

by aubrey.r.jones » 25 Jul 2013, 08:38

DrVonBraun wrote:Ok good to know, I think I will spend some time to build up my debug data once and then just render it each frame instead of building it each frame


Now that I'm back on a real keyboard, let me try to explain better.

When I say you need to re-use the Renderable, I mean literally just that. According to my delvings with RAD's Telemetry, the first time that a Renderable is used its shader is compiled. That shader compile takes (relatively) *forever*. It is that shader compile that makes up the vast majority of the overhead of the debug line drawing.

What this means is that if you literally just re-use the Renderable, you can rebind it with any vertex buffer you want, or re-write its vertex and attribute data with very little performance cost. The shader compile, which is most of the reason you get 1/3 FPS, only happens the first time you use the Renderable.

We redraw the whole debug universe each frame. And what we do isthis: have several FIFOs of warm Renderables, each FIFO holding a group of Renderables built with the same type and flags. When some element of our game requests to draw a 2D debug thing, it calls one of several methods I have in B2Debugger--DrawPolygon(), DrawPolyline(), etc. Those methods request a Renderable from the appropriate FIFO, fill the Renderable's VertexBuffer, and add the Renderable to the render list. Then, at the end of the World::Render() call, I have a "RenderDebugFrame()" method, which hands the render list off to TheGraphicsMgr::DrawRenderList.

Mind you, this works much better on nVidia than AMD (like, twice as well). I'm not sure why, but we've observed it quite consistently.
