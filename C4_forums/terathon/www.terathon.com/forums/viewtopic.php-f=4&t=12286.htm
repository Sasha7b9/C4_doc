by mschifter » 18 Oct 2012, 08:30

Hi Grognard,

C4 seems to be avid fan of centralized scene graph that does everything


I've worked with or helped develop 6 different 3D engines, and researched more than that. All of them used a scene graph data structure for rendering. Within that scene graph, you have a natural hierarchy defining scene sections, at a minimum. The closer you are to the root node, generally the larger the scene portion, so generally speaking, one can clip out larger chunks at a time so they don't get rendered. The less that gets through this clipping phase, the fewer the items that are sent to the card for rendering.

Then there's the concept of lists within the hierarchy. These might be found in each clipping section, or they might be in an entirely different area. This is because they have special rendering rules that forces their order to be later. This includes translucent items, shadows, and special shader items like lights.

Of course C4 uses the scene graph hierarchy for much more, including triggered areas, portal setup, etc. But it makes sense that these components exist along with their graphical components because drawing things in the correct order executes the code when it has its effect. So a trigger node is tested against player position only when the player is near the trigger node's location, and if the trigger fires, the player's position likely interacts with the trigger only at that moment.

Hope this helps,

Matt

by mschifter » 22 Oct 2012, 08:33

The techniques common in the simulation industry in dealing with the entire world using 32-bit floats includes the Universal Transverse Mercator projection, or UTM. The world is divided up into flat sections called UTM zones. Each zone has an inherent mapping to lat/long at its borders, and positions are represented considering each zone to have its own origin. The zone becomes part of the coordinate.

There's a wikipedia article here: http://en.wikipedia.org/wiki/Universal_Transverse_Mercator_coordinate_system

As you might guess, everything is well-established/proven. There is also a conversion between World Geodetic System (WGS 84) and UTM. WGS is used by GPS and the simulation industry (more current use than UTM).

These well-established standards may be worth a looksee if you have a huge area to represent, but need resolution down to feet or smaller.

by mschifter » 22 Oct 2012, 11:23

MrTesla/ALL:

I've seen and used an unlimited accuracy floating point library a few years back, and I think I used it for calculating constants at the start of an app, like pi. During run-time, you set the accuracy you want.

But it's not for real-time programming.

The last time I used fixed point integer math, floating point was very time consuming and it was on a separate chip (remember the old 80386 and 80387 fp chip?). Fixed point math incurs high performance penalties when you convert to and from floating point formats. It's only practical when you can do an entire algorithm in fixed point and then convert to fp after all the calculations needed for a relatively large chunk of time are complete, and of course only if the accuracy is adequate. Transfers between the integer pipelines and fp pipelines are "serialized" (in this case, meaning "not parallel"), and so simultaneous speculative execution is forced to stall the instruction pipeline before the integer results can be transferred to the fp pipeline.

These days, the main CPU contains several floating point units that operate in parallel, as well as several integer units. Math for floating point is a lot faster than it used to be. Last I checked, AMD used 5 floating point processor units and Intel used 3. AMD could calculate a 4x4 matrix multiply operation as a high performance specialization of the processor, and Intel could do a 3x3 matrix multiply.

Also, consider that both chip makers have algorithms that execute code out of order in an attempt to complete the operations faster, and you wind up with increased performance with that technology.

For SIMD math, which requires some processor register setup, you wind up with fp operations that run approximately one operation per clock cycle.

It's been a few years since I looked through Intel's processor documentation, but if you want to know what's practical and how long things should take, I recommend you go onto Intel and/or AMD's website(s), find the processor reference guide, user's guide, and Intel has a C++ optimization guide, and you will get the actual cost of math operations on current chips. Then again, actually running your algorithms and timing them gives you the real-world performance numbers you need.

Edit: One more point for you C++ programmers out there. If you aren't familiar with these, check out "Compiler Intrinsics," which are C++ functions that are written using assembly language that is specialized to a processor (right now, intel and AMD). I'm using Visual Studio Pro ed. version 2K8, and these are found in this help page: http://msdn.microsoft.com/en-us/library/tzkfha43.aspx These functions are very probably faster versions than anything you could code.

Regards,

Matt
PS -- another problem with fixed point math was substantial jitter. We used a 3d engine in 1995 (no longer available or usable) called BRender, and it had a fixed point mode (again, no comparisons here to C4), and it had terrible jitter problems. The point is, fixed point can cause you a world of problems in today's 3D environments, and IMHO you are asking for trouble if you try to use it.
