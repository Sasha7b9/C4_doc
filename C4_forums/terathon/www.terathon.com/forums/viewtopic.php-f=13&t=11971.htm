AMP : the middleware used by Wind of Luck

by TheRhinoDude » 24 Jun 2012, 16:53

Hey folks,

As I mentioned in Casper's Wind of Luck (WoL) announcement thread in the Showcase forum, I've been working with him and the rest of the Trazzy team since early 2010. Back in 2008 I started a project which has morphed into what today is AMP, which is an acronym for the Adaptive Middleware Platform.

AMP is an adaptive and location-independent Service Orientated Archicture (SOA) platfom that provides network services for MMO's and other online games and networked simulations and serious games. Some of the services include registration/account management, login/sessions, lobby/chat, patching and synchronization, world/zone management, tuple spaces, game simulation, auditing, payments/recurring billing, just to name a few. AMP also provides database services (db's and access libs) for everything from the world storage (avatars, zones, items, npcs, etc.) to account / CRM storage to content, knowledge base, issuse tracking, and much, much more.

So just what is an AMP Service? It's simple actually. At it's simplest definition, and AMP Service is a collection of interface methods that you can invoke, yet depending upon deployed configuration you may not necessarily know where they will be executed. That is what is meant by location independent. It supports client-server topologies upon deployment, but at it's core it's a graph architecture that can support many-to-many communications. So when working with the AMP core, you can really build any type of networked application. The AMP Game Services are simply one of the first problems we are tackling. From here on when I refer to "AMP", I'm referring to the Core + these Game Services.

AMP is all 100% generic and parts can be used for any networked PC game (and soon Mac and Linux) or networked simulation, not just something that looks like WoL or even a MMO. In fact, there is another team developing a non-MMO game with it right now.

One of the key aspects of AMP is it is designed to work with other technologies and can be used piece by piece; it is not a monolithic solution. For example, WoL uses AMP alongside RakNet, and performs networking with both of them. AMP does not pretend to be all things to all projects. Each service is indivdually deployable and separately accessible and optionally clusterable from all of the others (unlike RakNet where it all has to be compiled into your application even if you only use parts of it). You can use one, some, all or none of the AMP Services.

Furthermore, all services that depend on other services are lightly coupled using a hybrid interface/adapter pattern which easily allows services to be "glued" to third party implementations. Entire layers of the architecture can be replaced, and one of the upcoming features is the transport layer will be pluggable, so you won't even have to use AMP's built-in networking transports, and can instead be used on top of RakNet, ENet, and so forth.

Most AMP services are also highly extensible from the outisde using an XML configuration file for many settings, switches, and choices of behaviors. These configurations can be imported/exported to and from the AMP Master databases, for central managemet of all configurations, in a deployed environment. This is a key element to the adaptive "cloudiness" nature of AMP. Many of the tenets of the utility computing model went into the design fo the AMP architecture, making server management and game scaling a piece of cake, and eventually, automatic if desired.

Conversely, for simplified development these configurations can simply be XML files on your hard drive and will automatically be loaded from there. The official build process may then choose to use the AmpDbTool to merge these configurations into the database for deployment to a particular test or even production environment. Well over a decade of writing and managing server environments has taught me a lot of tricks, and these are all baked into AMP.

Alternatively, a few services also support optional plugins managed or native DLL's which can extend or even replace service features without code access, mitigating future code interation work. The plugin and adapter patterns are heavily used here and it is an extremely powerful paradigm. Two plugin interfaces are supported, so you can write your DLL either in managed code such as C#, or as a plain-jane native DLL with entrypoints. Eventually all services will support this plugin framework.

Of course, AMP will be available both with and without source code licenses, so you can alter the service code if you reallly want or need to. But I've tried to provide as many ways as possible to extend and alter it's behavior without having to make custom code modifications. The plugin interfaces are going to be sacred within major versions. The code inside...not so much.

One of the cooler features I'm working on with a third party right now is the scripting system which will provide a standard AMP Script Engine Plugin to be plugged into any of pluggable services, so you can script all of this service customization instead of writing your own DLL. You'll be able to remotely debug, automatically load and save scripts back to server with versioning, and so forth. This work is very preliminary so there isn't much to share about it at this point. If this doesn't make it into 1.0, it will very high in the roadmap.

Another one of the key points of AMP is it is a platform, not just middleware. In addition to being able to extend the stock services, you can of course write your own. The upcoming AmpCompiler will actually generate all of the proxies, stubs, and processors for you from your own interfaces. But unlike most complete MMO engine solutions, which AMP is eventually going to grow to be, it doesn't force you to the platform and require you to extend it as the platform designers saw fit. If you just want to use just a single AMP service such as the patcher in your project, then fine. Conversely, if you want to build your entire game's networking and backend around AMP, then fine. WoL for example is between these two extremes, athough it is closer to the later. It uses almost all of AMP's services except for the simulation services, for which they use RakNet for their own custom game simulation logic.

Finally, one of AMP's greatest strengths is it's high performance and scalability. A lot has been said above about flexility, replaceable tiers, plugins, adapter/interface patterns, and so forth. A seasoned software engineer will read these things and perhaps think one thing: SLOW. This couldn't be further from the truth. Absolute performance has been a critical point of AMP design from the beginning. The code has been extremely tuned and native code is used where it is needed to minimize bottlenecks (AMP is about 95% C# 5% native C). In short the architecture embraces high parallalism and object caching, and as such scales very well on modern high-core high-memory systems, which AMP leverage to their fullest.

For example, let's look at the AMP Login Service and what it takes to do a login. Performing a login isn't just about checking credentials. It of course includes all of the encryption and handshaking necessary with the client to securely establish a shared secret key for high performance secure communications, as well as overhead for checking blacklists, checking for malicious intent / attack recognition, as well as creating a unique session and identifier, tieing customers IP and shared secret key to that session, as well as loading the relevant bits of their account profile into the session for future reference. In short, a lot happens. So how many of these distinct logins can AMP process in a second?

- On a 5+ year old core duo @ 2ghz @ 2gb laptop, you can see ~250 logins per second.
- On a first generation i5 dual-core @ 2.93 ghz (HT enabled) @ 4gb, it jumps to ~900 login/sec.
- On a modern dual xeon 24 cores @ 2.26 ghz total (HT enabled) @ 16gb, it can handle ~5k logins per second.

Not quite near linear scalability, but close. Also of note is that deviation on the last example is < 5% no matter how many user accounts you have whether it is 10 or 1,000 or 10,000 or 100,000 or 1,000,000 or even 10,000,000. The key to these numbers is aggressive caching and focus on parallelism throughout the stack.

So if anybody has been wondering where I disapear to months at a time with nary a post here in the C4 forums, this is it: it means I am heads-down coding in AMP.

If anybody has any questions or would like some additional details, feel free ask away and if it's something I can share I will. I hope to have the website live in the next few months which will provide much more detail as well as a demo download of AMP itself. But at this point I'm still heads down finishing it all, and doing everything I can to make sure WoL is a success. When I get closer, probably as WoL beta approaches, I will put up a site and start taking Early Adopter orders, which will get free updates for life on the entire AMP suite including future products in the same product line.

In the meantime, to see AMP in action (albeit under the covers), check out Trazzy's site at http://www.trazzy.com. Almost everything at the site below the ASP.Net presentation layer is built upon nearly two-dozen different AMP services, and all data is stored in AMP db's. In fact, nearly every word you read on that dynamic site is stored in one of several globalzied AMP Content databases and accessed through it's content management service. In fact the only "deep feature" on the site not implemented on AMP are the forums, which uses the third party JitBitForum, but even that was integrated with AMP for single sign-on. In short, while the site itself is built on the ASP.Net for presentation layer only by another team, almost all of the functionality is implemented as AMP services by myself. This allows for an exceedingly tight integration between game and website, if desired.

Note that even though the site presentation layer is built in .Net, the entire set of AMP Services useful for building a website is made available through a library which is also PHP accessible. I obviously wanted to support PHP due ito it's ubiquity. If there is enough demand, someday I may also author WordPress, Joomla plugins, or DNN plugins. If I don't, hopefully somebody else will.

Note that when playing around with the site, especially for my friends here in the states, that it is hosted out of The Netherlands as Trazzy is a European company, and pages load accordingly.

Anyway let me know if any questions.

Thanks,

Sorry this isn't the short answer you're probably looking for...as frankly I don't have final prices figured in yet and don't want to share and have things change. However I have decided on the general product line and licensing models that I would like to get feedback on. Furthermore, the one thing I can say is that upon initial Early Adapter launch, it will be priced at 75% of what the total "AMP Master Suite" will be on 1.0 launch. More details below on what all that means.

First, there will be no percentage-based royalties, ever, even for binary editions. This choice meant doing things a bit differently though, so some of this may feel a bit different, and I'd appreciate feedback on it. Quite a bit of market research has actually gone into this already, as should be.

Second, all products will be available as both Binary and Source Editions. More on that later as it affects licensing and deployment. Binary costs will going to be very aggressive (ie low) as I want hobbyist developers and indies on a tight budget to be able to afford this. Note that you will be able to upgrade from Binary to Source at cost differential, no hidden tricks or fees.

Third, there will be many products, as I don't think it's fair to ask somebody to buy everything if they don't need it. It would be one thing if it was a monolithic engine where everything was tightly bound. If that were the case, it would just be one large big product for a single flat fee. But AMP is purposefully built to be exactly the opposite of this. You can pick and choose what you need. As such, the menu will be a la carte: you order and pay for what you eat.

For example, there is a lot to the AMP Patcher and Launcher. A ton of features, and a lot of engineering work that went into it. If you don't need it for your project because you don't have a launcher, or are only going to be sold on Steam for example, then you don't need this piece of technology. You shouldn't have to pay for it if you don't need it.

As such, the approach to our product lines will be that many different smaller products will extend a common AMP Core product. You buy the Core, and then only what you need to extend it.

But what if you "need" everything? Or what if you need only the game services, but are going to merge them with your own website and existing back-office billings, CRM and KB? While trying to be fair to those who just need a few services, we don't want others to feel like they are being nickel-and-dimed to death with add-on products. For these people, we will offer bundled "suites" so that they can be preconfigured groups of products, and save.

These are the planned suites and their products in them:

- AMP Foundation Suite : includes Core + Locator + Basic Data + Native Bridges product. Everybody needs this.
- AMP Back Office Suite : includes Foundation Suite + Web Services + Payment Service + Recurring Billing + Advanced Data
- AMP Patcher Suite : includes Foundation Suite + Patcher Service + Launcher App
- AMP Game Services Suite : includes Foundation Suite + User Services + Lobby Services + World Services
- AMP Master Suite : includes *everything*

So the Foundation Suite is included in all of the other suites. The Master Suite includes everything. Again, if you start with Foundation Suite you will be able to upgrade to another suite at no penalty if under active maintenance. The same goes for upgrading any of the other suites to Master suite. I'm not sure if we will offer cross-grades from individual products to suites though. That can get really messy to do, and can be abused. So we may not offer that. Right now I'm leaning against it.

All products and suites will have their own maintenance plan. Initial purchase gets you 1 year maintenance. Renewals are on a 1 year basis. Active maintenance entitles you to latest versions, private support forums, as well as private email group.

All developers need their own license. This includes developers using AMP API's, components or services, including authoring their own services, writing plugins for existing services, and so forth. A separate license will be available for script programmers only for teams that need this flexibility.

The Early Adopter will basically be a perpetual Master Suite license. So you will have access to everything going forward that falls under the banner "AMP". I haven't decided on pricing yet for the individual products much less the suite, but I have decided that it will be released on a sliding 75%, 50% and finally 25% discount up until launch. Once launched, the discount will disappear, along with perpetual updates for life. They may come back from time to time as incentives like a weekend sale or something, but I can't promise it.

Now back to binary vs. source licensing costs...as they pertain to MMO's / networked games where you run your own public server(s) using AMP, whether revenue generating or not.

Unlike many MMO solutions targeted towards independents AMP will be royalty-free in terms of your revenue, even for binary licenses. We are trying to make this very hobbyist and indie friendly, which means low up-front costs, and no oppressive royalties, and no excessive one-time deployment costs. But on the other hand, if you have a run-away hit and end up deploying lots of servers, we feel we deserve something other than the small up-front binary licensing fee.

So what we've come up with is really quite simple: Binary Editions pay little up front, pay a bit more per as servers are deployed, and a bit more money each month as you continue to run them, independent of revenue levels or the power of the server. Source Editions pay more up front, but have no server deployment fees (within your organization). Some details on this...

Binary Edition will require per-machine activation and recurring subscription for servers containing AMP functionality that is being directly or indirectly accessed by anybody outside your immediate organization (ie open beta testing, live production). Distributed application for internal or Intranet within your business organization only do not require server activation.

There will be two different per-server activations and subscriptions to choose from per game: revenue-generating, and non-revenue generating. Each license is independent of the number of cores, their speed, and total system memory. Activation is done over the Internet, and can be done from a different machine if necessary with our activation tool. Once activated, there will be a small monthly recurring subscription to keep that server running legally. These can be paid in advance if desired, at a discount, and are transferrable.

A local license server product will be available to simplify all of this so that your servers can do all of their licensing through this license proxy server automatically. Note that when a server license expires, it does NOT automatically stop working or bring down your game. It simply notifies you, and us if possible, that the license has expired. If after one week it has not been reactivated, it will still keep running, but if it is shut-down it will refuse to start back up until reactivated. If desired, you can of course pre-pay many months in advance. You can also "migrate" activations from machine to machine at no cost and no loss of remaining time.

Source Edition will have no such per-server activation and subscription. The Source Edition distributions will have the activation and license enforcement code removed, so source licensees can deploy binaries built from their source how they see fit, within your organization. There will be no server maintenance for support and upgrade assurance separate from the support and upgrade assurance for the source code license itself. Naturally, the source code is licensed for use by a single developer. Each developer that works on or needs to program to AMP services or components you have compiled with the Source Edition, also needs the Source Edition.

So as you can see, the Source Edition is a fundamentally different beast. It isn't just about ability to modify the source. Even if you never modify the source, you may wish to upgrade to source license for all of your developers as you near game launch purely for access to the alternate deployment and licensing model.

Again, our primary goal here is to provide flexible licensing models for hobbyists and small independents so that they don't have to pay much to get started, or a small fortune to progress into a public open beta and eventual launch. Furthermore, when an independent does develop a great game and is about to have a large, successful launch, then they have a choice between two different solutions: per server licensing, or upgrade to source licenses for all developer seats used in construction of the game.

So that's it. It's a bit different than the models that are out there, but as you can see our driving force has been to make sure that the decisions are in your hands, and that you can choose the model that works best for you no matter the size and funding level of your organization. We want hobbyist and small independent developers to get started and pay as little up front as possible. Serious independents will probably opt for the source licenses, maybe not at first, but will possibly upgrade to them as needed. Pro shops will likely just buy the source licenses up front without thinking twice about it.

We want to provide this flexibility to all, and still be a viable business model to us. And I think we've got a model that does that, but I would love to hear feedback, critiques, additional ideas, and so forth.

Thanks,

Jesse Meyer wrote:Another broad question: How does AMP play with virtualized servers?


Great question.

AMP doesn't distinguish between physical and virtual servers, and it works very well under virtualization. I do a lot of testing under VM's so that on my 8 test servers I can emulate much larger installations. AMP is in fact being used in a production virtualized environment right now.

However, with that said with AMP there is less of a reason to virtualize a server fulfilling only AMP server roles than there are for traditional server roles. AMP does reap fewer benefits from some of the primary reasons for virtualization: segmentation of server roles, and enhanced parallelism and utilization of hardware.

With AMP's centralized configuration of server roles, it is trivial to migrate server roles from one machine to another (in the future AMP will even do so automatically as needed if instructed to do so). Plus each service can optionally be hosted in its own app domain and therefore cannot affect other AMP services if one crashes. So if the primary reason for considering virtualization is isolation and/or segregation of AMP server roles, then you are really underutilizing one of the nice features of AMP.

Furthermore, with many traditional (read: old and poorly scalable) server implementations, virtualization is used as a good way to achieve scalability and better utilize hardware of server implementations that are not highly parallel. AMP is the exact opposite: it is exceedingly parallel and was designed from the ground up to be so. With some older servers, taking a 24-core box and creating (6) quad-cores out of it and running six clustered servers on WLBS was a great way to more effectively leverage the hardware, purely because the software wouldn't scale well beyond a few cores as it was not highly parallel. Virtualization was the answer to scaling this poorly written software. AMP doesn't suffer from that. If you tried the same trick with AMP login service, you would lose throughput, not increase it. That's in fact one of the tests I do to prove it's scalability.

However, if you are virtualizing for other reasons, for example let's say you know that eventually the current environment will scale to a certain number of servers and you want to test on such an environment ahead of time (aka evolution planning and validation), then virtualizing ahead of time has obvious benefits and AMP will play along just fine, with a few minor caveats.

One such caveat is that some of the advanced clustering and load balancing features of AMP which can be configured to use optional algorithms that take into account network port saturation. These can work improperly under VM's if the host network adapter is not properly segmented to the individual hosted VM's. If improperly configured then AMP clustering can actually cause a virtualized server to be under loaded because it thinks the network load for that machine is higher than it really is. To avoid this you both have to segment and cap network traffic among the VM's (something not all VM products allow you to do), or else you need to avoid using the load balance algorithms which take into account network saturation. Five balancing algorithms are available out of the box, three of which do not use network saturation. Plus it's easy to extend the cluster service to write your own or tweak the stock algorithms. So there are a lot of ways around this "issue".

With respect to binary license activation and subscription, as mentioned above virtual machines are considered real machines, and as such are licensed and activated the same way. The benefits of "any cores / any amount of memory" for the license go both ways. As discussed above, there is less of a benefit to segregating server roles to their own virtual machines with AMP than there are with other more traditional server software. And virtualizing in order to achieve scalability and better hardware utilization out of non-scalable server software is a moot point with AMP.

But if this point of licensing still bothers some (and I understand it may), one of the things to keep in mind is that there will be a big difference in cost between revenue generating and non-revenue generating binary server fees. Furthermore, until the servers are customer facing, there is no machine licensing fees anyway: you can run off of your developer licenses. These two together greatly lessen the impact of virtual server licening overhead.

Typically, when using many virtual machines to perform environment evolution planning and validation, this will all be done behind the scenes and not with customer facing servers. And even if they are, this work will usually be done during beta, and not live. So the licensing overhead cost of running the VM's for these tests will either be none (if you aren't customer facing), or minimal (if you are customer facing, but not yet generating revenue). By the time you are generating revenue, the environment should be expanded, and you will have money coming in to offset the small monthly fees for the servers. Also, note that these fees will be small compared to bandwidth costs used by the servers, so we aren't talking a lot of money per server to begin with.

Let me know if any questions / thoughts / concerns…

Thanks,
