Re: Clients/Server Not In Sync (Floating Characters)

by Benjamin Dobell » 29 May 2009, 12:26

Eric, I think this is what is happening.

The client is receiving packets out of order. The client accepts the packets and acknowledges this to the server which makes sense. However in my case occasionally all 32 of the client's receive packets end up in the receiveUsedList however none of them are the "next" packet so they just stay there. Because all the receive packets are in use the client is then unable to receive the "next" packet. This incapacitates the client.

Meanwhile, the server keeps resending packets that the client hasn't acknowledged. This causes all 64 of the send data packets to end up in the reliableSentList of the NetworkConnection connected to the client. Obviously this then means the server is unable to send the client's "next" packet to the client even if it could receive it.

The solution, as far as I can tell, would be to put a limit on the number of out of order packets that can be received by C4. So once the C4 reaches this limit it just discards any more out of order packets and doesn't send an acknowledgement packet to the sender, this way the sender will keep them in it's reliableSentList and resend them later after the the receiver's "next" packet has got through.

by Benjamin Dobell » 30 May 2009, 05:09

Sorry both the original and the edited parts of that last post are true in some way.

The server is still able to send reliable messages to clients if the reliable packet already resides in the reliableSentList. However any new reliable messages that are meant to be sent are lost for good (because there are no available sendDataPackets) which results in massive de-synchronisation. The only solution I can think of would require a bit of re-design of the low level networking system.

Presumably the limited number of packets was a design choice for improved speed as accessing an array is going to be quicker than allocating and de-allocating memory all the time. However I don't think it is totally practical for reliable messages/packets. The point of reliable packets is that they will always be received by the client. If the client is too slow to acknowledge reliable packets the server's reliableSentList will fill up. Then if server has new reliable packets that need to be sent then they will be discarded and the client will never receive them, aka Bad news! For unreliable packets the buffer approach makes sense. However for reliable packets would a dynamic memory allocation approach be more appropriate? Even if some sort of resizable array was used so allocation only occurs when it's really necessary.

Eric, what do you think?
