by cbken » 14 Jan 2014, 00:02

I'm with Eric on this one, the GPU is handling it correctly and it's really nothing to worry about. And in any case you can't really do anything about it.

If you want to dig into it more out of curiosity then I'd say the easiest is probably to hack a .tex file and replace the mipmap levels there with different data. I don't know the layout of a tex file but when compressed, the data is of a known size and I'd imagine by taking a closer look at the texture saving/loading code it can be sorted out and the file offsets for the various mipmap levels can be determined. Then just replace each level with data from same level in another compressed texture. This can be done with some file editor or by hacking together a simple tool that will assemble a tex file.

by Jesse Meyer » 14 Jan 2014, 00:19

cjacket wrote:I don't know, but I'm almost gathering from your second post Mack, that you are possibly trying to make sure you aren't creating textures that are too big to be efficiently used. ...


And that kind of optimization only really makes sense if the game is forced to run at a particular resolution for all users. AFAIK, GPUs consider a few metrics, including window resolution, when determining the proper mipmap level.

It is important to size textures properly, but that's pretty straight forward if it's known how much screen space and time an object takes up on average throughout a session. For visually oriented individuals, I can see this being useful, but professional artists are already trained to deal with this as a second nature that the feature probably wouldn't be used much by them anyway.
