Re: Networked player movement in Game code

by kauaiBlake » 29 May 2012, 22:38

So its been a while since I wrote the networking code for Crashday using Raknet, what I remember for sure is that we had the client controlling their car directly and immediately. The client would then send its position, velocity, accel info to the server and the server would forward the received position to account for ping time as a prediction, then putting that prediction through the physics engine to account for terrain, ramps, and other car collisions. We then interpolated from the the last version of the car prediction to the new car prediction over a short time to smooth things out. We gave the client a small window of where their car could be, based on the previous physics, to try and prevent hacks by the client, plus we put in a few more tricks.

I am the first to admit that the implementation could have used lots of refining, but it turned out to work pretty well, and the player had the feeling of being in direct control of their car.

Re: Networked player movement in Game code

by Infernal » 24 Jul 2012, 17:52

The reason you experience high network bandwidth for one character on the server or just two is that this method doesn't employ any means of delta compression.

What is delta compression? If for instance your movement vector hasn't changed from one input frame to another, instead of sending the whole vector a second time, your deltacompression layer (on top of the network messenger) would replace it with a single bit indicating that the delta compression layer on the server should simply replace that bit with the vector information from the previous message. In the case that the vector has indeed changed, the tradeoff is including the extra bit immediately before the full vector data. Slightly higher price for new data for significant savings for repeated data.

The quake 3 source code has a good demonstration of delta compression in practice. The Quake 4 sdk also does as this is really all game level code and not engine level in those games/engines.

In those games, the server also delta compresses snapshot information sent to players detailing the state of the "visible" objects (to each player) in the world.

This reduces network bandwidth significantly as you can understand that each frame is roughly 11ms or more and humans cannot not change input multiple times within 11ms.

The tutorial is great for a start but there are further issues to deal with. Especially determinism within the engine physics.

by yaure » 03 Aug 2012, 07:08

It's been a while since I looked into the network code. I remember C4 on windows uses Winsock2 Event Objects or Async sockets, which is not the best solution for a very large amount of concurrent connections. There is the Overlapped I/O and Completion Port model that provides performance for using Winsock. It is not the easiest thing to implement. Back at uni I was tempted to change the underlying network code to use it but didn't in the end as I don't think my implementation which was used in one of my large courseworks was good enough in real world production.
