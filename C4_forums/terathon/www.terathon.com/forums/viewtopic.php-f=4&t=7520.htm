I've been fiddling with one possible solution based on your idea of using cameras attached to the enemies heads.
I have no idea if this will work in the end, but basically I disable all lights, set the ambient color to completely black and render the scene into a small viewport area(I couldn't figure out how to render to a separate texture so for now I render to the screen)
Before rendering this small area, I would hide the player model, and instead show a box or cylinder with a material that has it's emissive color set to full magenta.
The only thing that should be visible in the small area now is the magenta box.
Now, if I scan this small area counting all magenta pixels and divide that number by the total amount of pixels in the area I should get a value which I could use to determine how visible the player is to the enemy.

Here are two screenshots.

Player fully visible (check the visibility area at the top left corner)

Player partly visible


Here is some code...
Code: Select all
void GameWorld::Render(void)
{
   // Render the world normally
   World::Render();
   World::EndRendering(); // Force post processing

   // Render miniview

   // First put out the lights...
   Array<Node*> lights;
   Node* root = GetRootNode();
   Node* node = root;
   while(node)
   {
      if(node->GetNodeType() == kNodeLight)
      {
         if ( !(node->GetNodeFlags() & kNodeDisabled))
         {
            node->Disable();
            lights.AddElement(node);
         }
      }

      node = root->GetNextNode(node);
   }

   FrustumCamera *camera = GetCamera();
   FrustumCameraObject *object = camera->GetObject();
   ZoneObject* zobj = static_cast<Zone*>(root)->GetObject();

   Rect saveRect = object->GetViewRect();
   float saveAspect = object->GetAspectRatio();
   ColorRGBA saveAmbient = zobj->GetAmbientLight();

   object->SetViewRect(Rect(0, 0, 160, 120));
   object->SetAspectRatio(120.0F / 160.0F);
   zobj->SetAmbientLight(ColorRGBA(0.0f,0.0f,0.0f));
   World::Render();

   // Restore everything as it was
   object->SetViewRect(saveRect);
   object->SetAspectRatio(saveAspect);
   zobj->SetAmbientLight(saveAmbient);

   for (int i=0;i<lights.GetElementCount();i++)
   {
      lights[i]->Enable();
   }
   lights.Purge();

}

Something like this...

// Declaration
Pixel* visImg;
...
// In the constructor
long pixelCount = 160 * 120;
visImg = new Pixel[pixelCount]; // Don't forget the delete[] in the destructor

// In the render function
TheGraphicsMgr->ReadImageBuffer(Rect(0,0,160,120),visImg,160,Point(0,0));

// Process the image
long pixelCount = 160 * 120;
long foundpixels = 0;
float visibility = 0.0f;

for(long i=0; i < pixelcount; i++)
{
if ( (visImg[i] == 0x00FF40FF) ) // Added default ambience here(as I mentioned above) not needed though if amb = black.
foundpixels++;
}
visibility = 100.0 * ((float)foundpixels / (float)pixelcount); // In percent

Here's another idea:

Maintain a list of enemies that are in your zone/neighboring zone.

Cast a ray from you to everyone on your list. If you connect, do more processing. You can optimize in the same way Sven-Bertil Blom discussed. You can compare ray to NPC front to see if he's facing you. Cull your list based on distance...

This seems a bit simpler. Also, in the currently discusses method what would the NPC do if you run out into the open then hide behind a corner? Processing where you went from your vision render would be a lot of work. With the ray cast, if you disappear from view you have a Point3D of your last known location... you can send your NPC to that location to look for you.

I'm not sure how demanding World::QueryWorld is? From reading the docs the exclude option seems a bit crappy in that even though a geometry might be excluded you're still testing for collision, then throwing out the results if the exclusion mask is set. (plus, you're probably going to want collision on everything)

It would be best to make your own version of QueryWorld which only iterates through a specific type of geometry/collider. If it only iterated through floors, walls, doors, barrels, boxes, etc. I'd guess that you'd have no problem with performance.

Unfortunately, I think you're going to continue running into problems while going this route. The engine wasn't really designed to do what you're doing, but some additions that I'm planning to make in the 1.6.x-1.7 timeframe should fix the timing problems that you're seeing. You don't need to cast a cone, just a single point. Pick one point on the NPC's head and have the players point be some general location, like upper chest. With this method you're faking NPC vision: is it possible to have direct line of sight between NPC and player -> if yes: do more calculations to simulate NPC vision.

There are a few cases this won't catch, like if only your arm or legs are visible to the NPC, but it's always going to be give and take.

This is what I was originally considering but there are a number of problems with it, and obviously it depends how accurate you need to be. I mean you can do a very simple system but it wouldn't be very good and you can't account for things like which way the AI's head is turned, peripheral vision etc.

Here is one way you might like to try, I think with the limited range and using appropriate masks, the ray casts should be fairly efficient - but Eric would need to confirm this.

1. Check which AI are in sight range of the player based on coordinates, these are the only AI you need to check and will quickly cull the AI list that need to be tested.

2. Cast a THICK ray in front of each AI on the list using their facing vector, view distance and adjusting for the direction the head is turned.

This ray needs to be thick to account for the AI's vision/peripheral vision - since we can't use a cone you basically make the rays radius to match what the end of the cone would be anyway. This is probably more accurate than a cone anyway, and more realistic to handle peripheral vision. Now this ray can mask everything except the player, all we are trying to do is see if this thick ray collides with the player.

3. If the thick ray collides with the player then we need to do some extra testing to determine if the AI can see the player. To do this you just cast a few extra rays depending on how accurate you want it.

These rays should be THIN. In this case you might cast 5 rays to different points on the players body, from the AI's head/eyes. So maybe cast one ray from the AI to the players head, one to each foot and one to each shoulder. If any of these rays reach the player without colliding with something first, then the AI can see the player. This will even handle cases where the player has a foot sticking out or shoulders sticking out.

Now those 3 steps are actually very easy to implement, and are quite flexible as to how accurate you want the detection to be.

I'm not sure if there is really a more efficient way to do it, you could probably do some basic mathematical/vector calculations for the vision but that is essentially what the raycast are doing anyway.

Step 2 could actually be replaced with a single raycast from AI's head to players chest, and then you can compare this vector with the facing vector of the AI and see if the angles are in range. This might be more efficient than a thick ray i'm not sure.
