by Adam Golden » 30 Sep 2010, 15:22

Eric Lengyel wrote:The number of cores shouldn't really affect the speed of an "overgrowth" mode, unless the trees are skinned.

Are you using impostors for the trees?

Visibility determination runs on a secondary core. When I was using the main thread for everything initially, I was limited to about 5,000 elements of foliage, and reaching 25-30fps levels doing that. Once I changed things over to the Job Manager I could have 15-20,000 in a level at 30+. If I allow a secondary thread on a single core processor that might not have the same benefit. Although I suppose I could allow the toggle for everyone, just in case

I'm not using impostors at the moment, mainly due to terrain blocks repositioning during gameplay - I'm under the impression that if I move nodes containing impostors then the buffer has to be rebuilt, unless I loaded a different copy of each model for each block (of which there are 16). At the moment I only have 3 types of foliage (2 bushes and a tree), which are all assigned random scale and rotation (which isn't supported by impostors at the moment either), but in later versions of the game there will be 20+ types in a level. All these things pretty much prevent the use of impostors.

Edit: We did talk once about the Job Manager still allocating a separate thread even on single cores, I remember being excited at the time. I guess if the person has a good single processor, it would still work well enough, so I'll definitely allow this for everyone who wants to try it. Also, I just mentioned this map has 16 blocks (4x4) but some maps might have ^2 as many if they're larger, and I've been considering multiple layers as well for the future (dropping through a hole onto a map underneath), so rebuilding the entire buffer at that scale would probably cause a lot of hiccups (?). In addition, I'll have collision with foliage implemented soon (bumping into bushes shaking them and causing rustling sounds), which would be transforming the node containing the impostor, which might also cause rebuilding to occur. I really like the impostors it just seems like a lot of things I'm doing run contrary to what it's intended for.

Re: Wingball 0.5

by Adam Golden » 30 Sep 2010, 18:18

Amo wrote:Other thing. You wouldn't mind giving a short hint how you achieved the speedometer like thingy interface (with the color gradient). Jack and me thought about how to achieve it and came up with the idea of a blend map or with a crap load of different parts, read: every single stripe.
What did you do? If you are willing to tell
And if the question may sound stupid, consider that it is almost 1am over here...

I made an array of Window classes with no background etc., then added a subnode of a single "tick" of the gauge to each to them (an ImageElement), and positioned it in -y a given distance from the origin that was appropriate to line up with where it goes on the background from the center of the gauge. Those ticks are in a matching array of ImageElements for simplicity. Kind of like an "i", where the dot at the top is the single tick graphic, and the bottom of it is the center of the Window it's on (all of which are subnodes of another Window for the individual gauge itself, which is positioned at the center of that area). Then in the for loop that constructs this, I rotate the transform of each of the Windows to the proper degree based on the index, so they're rotating from the bottom of the "i" around center. Then in a Move function of the class that owns the gauge, (derived from Window), I step through the array and if the color of the ImageElement should change since the last frame it will update it. Very lightweight approach, considering you're only updating 2-3 elements in a frame at most per gauge. Every tick is either color A or color B, except the last tick that's lit up, which can be anywhere from 0.0 to 1.0 times the channels of the final color. I tried approaching it several other ways but settled on this. I could put them closer so they touch, and could make them thinner and use more of them so it looks like it's "filling up" smoothly as opposed to the digital feel, but I like the space between them and I'm happy with it as is (mostly).

What I would like to see in the engine is a way to mask 1 image with an external alpha source. So I'd be able to make a round mini-map that fades at the perimeter and just shift the texture coordinates of the map texture based on the player's position. As it stands I would need to make it square to achieve that easily... otherwise I think I'd need to use a renderable list for which I'd have to work out all vertex positions and UVs programmatically for the disc, which I'm not really up for if I can help it

Edit:
a crap load of different parts, read: every single stripe.

That's what I did, but it doesn't matter if you're only updating what needs to be updated (as I said, 2-3 elements per gauge changing per frame in most cases). Considering everything else in a game, the memory footprint of even 100 small elements is negligible to begin with, and if you don't just arbitrarily update everything it shouldn't make a dent on performance.
