by Zephir62 » 13 Nov 2006, 19:25

I've had the same problem. The only way to fix it is to save the envelopes before applying the Reset XForm trick. You can save the envelopes in 3DS Max in the last(or second to last, forget which) drop-down menu in the Skin modifier. After applying the Xform box trick script to the mesh, reapply the skin modifier and in that same drop-down menu click the 'Load' button. Find the file you saved the envelopes to and there you go!

Now, I had problems with this in which the Collada Max exporter will crash when exporting after loading up the envelopes from a file. I submitted this to Bugzilla and they told me that the problem was fixed in their developemental build and if you guys have this problem too I'll upload the script file.

There is also a bug within C4 which is also related to the above-mentioned bug. I sent a .dae file to Eric a day ago so hopefully he will have this fixed soon if anyone else has this problem.


Edit:

For future purposes until the scaling problem is fixed, follow this method to save yourself time as scaling with IK links doesn't work very well.

by Zephir62 » 13 Nov 2006, 23:32

C4ColladaImporter.cpp : Line 3610 from build 129

Add the following two lines of code:

Code: Select all
if ((attribute == "JOINT") && (static_cast<Collada::Input *>(element)->GetInputIndex() == -1))
static_cast<Collada::Input *>(element)->SetInputIndex(0);


That will patch the code so your models will import perfectly fine for now but hopefully Eric will release a more official patch.

Edit:

for context, the code just above it should look like:
Code: Select all
else if (attribute == "INTERPOLATION") semantic = Collada::kSemanticInterpolation;
else if (attribute == "IN_TANGENT") semantic = Collada::kSemanticInTangent;
else if (attribute == "OUT_TANGENT") semantic = Collada::kSemanticOutTangent;

static_cast<Collada::Input *>(element)->SetInputSemantic(semantic);



--

by Eric Lengyel » 14 Nov 2006, 13:37

The source of one of the problems is that the Collada file contains vertices that are influenced by one bone with a weight of zero. The importer automatically removes these influences, but in these cases, it drops the bone count to zero. But the skinning code that runs when rendering assumes at least one bone. I don't see how this could be made to render correctly because if the zero-weight bone is left in, then the vertex will always be placed at the origin. I'm still looking into it.

by Eric Lengyel » 14 Nov 2006, 20:19

If I allow zero weights, then the character imports successfully, but it renders with a bunch of vertices at the origin (as expected). You'll notice that the Feeling Viewer shows the same problem. Since there's no correct way to fix this (because it's bad data), I'm going to modify the importer so that in cases where a vertex is influenced by one bone with weight zero, the weight will be changed to one. This will avoid the need to put extra checks in the skinning code that would slow it down. It will just render a different incorrect mesh than the Feeling Viewer does.
