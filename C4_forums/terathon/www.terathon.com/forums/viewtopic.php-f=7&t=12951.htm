Hello,

I'm just starting to get my head around "real" game programming, after some years of web development.

I would like to create a multiplayer game with about 10-20 players per game, but host all of these games on my server (there are permanent things in and between those games). That would mean that the same codebase is used for a master server (to use the same network functions), game server and client. Also I'm curious how much overhead it would cost to initialise everything again for each game.

Re: Dedicated Server hosting multiple Games

by DrVonBraun » 31 May 2013, 11:59

Here is what I did for my client server game:
First I must say I am not using the C4 network module but Raknet, because I already had a system going before I switched the client to C4 so I didnt want to bother converting the network code, so I cant say much about the C4 network API.

The server is clearly different from the client. it uses a different representation of the world, often much simpler. For example when you load a world in the client and add a character to it, you have the full character in RAM with the skeleton etc pp. On the server, basically all you need to represent the character is a box or maybe a dome physics shape.

The world representation can be different on the server. In the past I had a much simplified world there, basically a low level LOD that I used for coarse object placement and then let the client figure out the actual Z value when rendering each object. The idea was to save memory on the server. However this led to more problems than it was worth. memory is cheap these days, so dont bother. My recommendation would be to load the world completely on the server, but when you place dynamic objects, use a simplified shape to represent them.

As for physics, I tried to use the C4 physics system in that scenario and had to give up. It wasn't possible for me to keep the physics representation in sync on all machines and the server. So basically I am working with a simple system where I move the objects on the server without physics, except gravity which I compute manually for jumps. It all depends. I guess it may be possible to have physics run in sync if the physics engine is deterministic, but I am not sure here. If there is a single random call somewhere in it, it will clearly diverge at some point in time. So less is more in my opiinion, especially when you're just beginning with client server programming. You dont want to deal with those details which, in the end, are just a cool-factor in game but nothing that contributes to the game play, unless you have a racing game, space game etc where the physical features of an object are central to the game itself. In an RPG or combat simulator, its negligible.

Keep a copy of the static world data, that is the terrain, houses, etc on the client. Transmit the dynamic objects from the server as they come into the visibility scope of the player. Keep a representation of the player on the server with position and monitor the objects around it based on distance and then send the information about what he sees or of what he looses scope to the client. Keep static data for those objects on the client, that is of course the 3D model or things like armor value, armament etc. Minimize the amount of data you send.

When moving objects, make it so that the client initiates a move, the server then creates a move object and moves the item in the given direction with the given speed. When you create that, send a command to all clients so they can start a similar move. If you do it right, client and server can move without ever sending another data package until the move terminates. When that happens, send the position from the server to the client and let them correct the difference that they probably have accumulated so they represent the server position. You can do that with a slide movement to make it nicer or with a sudden jump.

And one more thing: Never trust the client. use client input only to initiate actins on the server, but verify the parameters to protect against hacking. Never let the client compute something and then just accept the result on the server. Always compute data on the server and send to the clients.

Not sure what else I can say, but regarding your post: Assume from the start that the server and client code are different. This is not a peer to peer scenario, so they have to contain different content. Feel free to ask specific questions, I try to answer if I can

Re: Dedicated Server hosting multiple Games

by miken » 31 May 2013, 17:02

We did some rework of C4 ourselves so that we could have a separate client and server C4::World in the same process. It's not exactly what you're looking for but we ran into issues that you will too

There's a few things you'll run into:

- TheMessageMgr. This is going to be the core of your pain. We had to do extensive rework of this to support multiple worlds, especially related to ControllerMessages.
- The WorldMgr has the notion of a "current world" - this assumes there's only one world, so this needs to be eliminated. You'll need to modify the game loop to tick a list of worlds
- TheNetworkMgr - I had some trouble getting two sockets in the same process, we have our own network stack so we don't use TheNetworkMgr at all

The other thing we did was change the ControllerRegistration mechanism so that we could actually instantiate different controller classes in the client and server worlds. This is pretty essential to being able to split the client and server code. This has major serialization-related ramifications that are difficult to work around, so we have further changes planned to revamp the controller serialization code

The short answer: this is a bunch of work to get going. Hope this helps

Of course, I wouldn't recommend hosting more than one game in a process anyway, as bugs/crashes from one game will be able to trash other games, which is undesirable.

by DrVonBraun » 31 May 2013, 22:09

The way I have things set up here is one VC solution for everything with projects according to the following schema:

- A client EXE or now, rather a client DLL that works with C4 and which is the basic executable
- A client static library or DLL if you prefere where nearly ALL of the code is that actually handles stuff. Called by the above Client DLL

- A Server EXE that executes the server or, if you have C4 on the server, same setup as above, a DLL to be called by C4

- A shared library (I prefere static link since it avoids some problems) that holds code and data that is included by client and server because it is shared

Why the dualisim on client side? If you made one monolithic DLL for the client you will run into problems when you want to debug multiple clients. With the above setup, you simply copy the main client DLL project (the one thats called by C4 directly) and you can debug a second client or repeat the step and have as many clients as you want to debug.

I used to have different solutions for client and server but that got out of hand since I had multiple server programs for a distributed server approach (actually I have one master control server that holds the main logic and several spatial servers that handle the C4 part and can run on different machines to distribute the load) and having each in their own Visual Studio instance sucks big time, so the one solution setup works for me. You can still remote debug client and server on different machines.

The headless server is actually just a release mode solution. In debug mode, the server will be a regular C4 server that opens a window but you can make it tiny and if you dont place a camera, nothing will be rendered during debug and when you do the release mode, you have headless server without that window.

As for the above advise with controllers and managers etc, this is probably just my personal style, but I minimize the use of C4 on the server side as much as possible because I think it makes things much easier when you can design the server part based on the necessity of the server and not based on what constructs the C4 engine requires you to have. C4 is great for single player games where you serialize the state of the whole world for the next session and I assume its also great for P2P games (dont have any experience with that though but it sounds like C4 handles it well). For a client server setup I would advise against designing your server around C4. Use C4 to load the world, use it to place items, use it to detect collisions, detect the terrain Z value, the topographic situation for your characters etc, but dont get into the controller, registratiors etc. My spatial server consists of a C4 world that is loaded, Objects that are derived from C4 nodes and skeleton Controllers that basically do nothing and everything else is handled in code that I develop based on the situational necessity.

The client is a totally different thing though. Here you must work closely with the way C4 wants you to do things. One feature I dont use at all is the C4 serialization, since that would be available only on the client and there is nothing to serialize since the dynamic objects come from the server.

Another thing to keep out is the floating point problem I learned about only recently. Anything thats more than about 5Km from the coordinate origin will start to jiggle because the floating point exactness gets lost, which is probably a big problem for a space game. On the client you can offset the origin and bring the camera back close to the new origin and then just use the offset for all positions. On the server I would imagine you will have to find a different solution.

You wont be able to run multiple C4 applications on the same machine so you cant partition the space on the server side and tun multiple C4 servers without having multiple machines. You could for instance give "dimension" attribute to each object and place them all around the origin in 5Km sectors. So for sintacne planet A is on position 10/10/10 and planet B is on position 5010/5010/5010 so 5 Km or LIghtyears or whatever away, but you relocate planet B to 10/10/10 but you keep an extra dimension flag and when it comes to visibility or approachibility for a spaceship on coordinate 5/5/5 it sees planet A but not planet B due to it's dimension flag. Just one of lots of solutions.

I heard the physics system of C4 got completely rewritten, are you talking about the old or the new one causing problems? And are there replacements which are known to be more deterministic?

My failure was just recently so it was with the 2.10 version, I dont think there is a major change in the physics for Version 3.0. You would have to ask somebody else about that, I wasn't able to keep client and server in sync. Perhaps it is possible on a P2P game where the bandwidth doesnt matter but over the internet you cant send correctional values every second or so, so it didnt work for me

Sevenos wrote:1) Use a shared library, keep client and server code separate.


I would say yes. There are surprisingly few code elements you will actually share. The majority are data tables. I would create one class per major datatable in the shared library and make most of the access function static to avoid including a table multiple times in the code. Say you have a table to access static values for ship types in your case. That involves probably a structure that defines the data per ship type, an enum for all shiptypes and an array with one entry per ship type. I would create the following general outlay in a separate H file that goes into the static library and is included by the static library, client and server:
Code: Select all
#ifndef SHIPTYPES_H
#define SHIPTYPES_H
enum E_Shiptype.....

struct S_SHIPTYPE.....

#endif

#ifdef SHIPTYPES_CPP
static S_SHIPTYPES as_shiptypes[] =
{
... one line per shiptype
};
#endif


And in the static library one class Shiptype_Static with a staticfunction like this:
Code: Select all
static const S_SHIPTYPE & Get_Shiptype_Data( E_SHIPTYPE );



And in the corresponding CPP file include this line:
Code: Select all
#define SHIPTYPES_CPP
#include "STATIC_SHIPTYPES.H" // That is the above H file


Now you can include that H file anywhere you want the shiptype access and have access to the enum and the structure, but the array is included only within that static class and then exposed through the static access function. That way you only have to keep one file updated and have the definitions and the static array in one location. I find that more convenient. Of course it means that anybody with access to the file can read the array, but it depends on your environment. If you're working alone like me that isnt a concern, if I worked with colleagues or so I would probably chose a different approach.

Sevenos wrote:2) Handling multiple sessions in one process would include big reworks and risk

If you mean runnning multiple servers for not-connected worlds, yes.

Sevenos wrote:3) Can't run multiple instances of C4 on the same machine (why is that?)

Mostly yes, that thread wtblife mentioned didnt lead to a real conclusion I believe, there were still questions open. I would argue, why would you want to run multiple instances of C4 anyway. If it's a client application your machine would be hopelessly overloaded with rendering and if it's a server, it will be overloaded with servicing user requests, so there is not really a point in my eyes. If you develop a client server game, you wont get around having 2-3 machines.

Sevenos wrote:It sounds like building the server completely without the game engine might be a good way to go. That would of course turn some tasks to be more complex, but I think the nature of the game would allow it. Have to think about what I really need on the server.


Again we are talking about a real client server application here, not just a P2P game with one machine standing out in the way that it's not used as a play console but handles certain aspects of the session in a central manner. If so, I would say yes. The server will be completely different from the client code and attempting any of the P2P techniques will lead to disaster. I have one multiplayer game running for 8 years now and I am working on this new one for several years now and the completely separate approach served me well. Especially this past half year that I spend switching my client over to C4 went relatively well due to the fact that the server logic is mostly unaffected by the switch, except the spatial representation part.

You could use the C4 engine in your server to load a world and position objects, but the physics will be a problem. In my case, I chose that path becasue I need to edit levels. In case of a space game I would probably not use C4 on the server side. Placing solar systems is something I wouldnt want to do in any 3D editor, its better done in a table in code and ships dont use sophisticated physics. Apply force impulses and keep the ship moving until another force applies. That little bit of gravitation that planets and stars influence on a ship is something you can handle yourself.

by jwatte » 03 Jun 2013, 11:21

You will probably want a "matchmaker" process that players connect to, and get told about where their game server is running.
Then, players connect to that game server.
You can run multiple game servers on a single machine if they each listen to a different port -- so the "where" part of where each client connects to needs to include the port number.
On Windows, the C4 executable uses a mutex to prevent multiple instances of the process on the same machine. You can disable this. Make sure each process uses a different working directory for writable files like logs etc if you do this.
Personally, I'd rather run the servers on Linux than Windows; setting up and managing the multiple processes would be simpler and more robust with less custom coding needed.
