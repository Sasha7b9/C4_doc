Here's the list from the Features page. It doesn't include the new stuff that will be released in a couple days. You can check out the Release Notes to see what's coming.

Full-scene dynamic lighting and shadows
  • Support for five different fundamental light source types. More
  • All lights and shadows rendered in real time at global scale.
  • Spot and cube light texture projections.
  • Precomputed ambient light volumes.
  • Three fully orthogonal shadow rendering techniques.
  • Shadow volume clipping and scissor optimizations.
Advanced per-pixel shading capabilities
  • Comprehensive bump mapping support.
  • Enhanced parallax mapping.
  • Horizon mapping.
  • Ambient lighting volumes.
  • Gloss-mapped specular reflections.
  • Cube environment mapping.
  • Cook-Torrance microfacet surface reflection.
  • Bumpy reflection and refraction.
  • Realistic water shading.
Scene graph
  • Extremely clean class hierarchy for scene graph nodes, including geometries, cameras, lights, sounds, zones, portals, triggers, markers, and special effects.
  • General state serialization support for saving worlds.
  • Quick save and quick load capabilities.
  • Separation between per-instance and shared data.
  • External scene graph referencing from within another scene graph.
State-of-the-art portal system
  • Efficient large-scale visibility determination.
  • Advanced interzone lighting analysis performed in real time.
  • Special support for mirrors and remote portals.
High-level controller system
  • Powerful hierarchical animation blending system.
  • Handles state messaging in a multiplayer environment.
  • Powerful scripting system that can be extended with custom actions.
  • Cleanly extensible design and integration with the tools.
Special effects
  • Full-scene cinematic motion blur. More
  • Volumetric fog with multiple density functions. More
  • Interactive in-game interface panels. More
  • High-quality procedural fire effects.
  • Fully extensible particle systems.
  • Real-time fluid surface simulation.
  • Real-time cloth simulation.
  • Surface markings on arbitrary geometry.
  • Emission glow and specular bloom effects.
Sound manager
  • Fully spatialized 3D sound effects.
  • Doppler shift and other frequency effects.
  • High-precision sound travel delay.
  • Atmospheric absorption effects.
  • Reverberation with multiple simultaneous environments.
  • Directional sounds with cone attenuation.
  • Obstruction attenuation applied to direct and reflected paths.
  • Frequency-dependent volume settings for all effects.
  • Permeation system determines how far sounds travel through interiors.
  • Unlimited streaming music channels with seamless looping and concatenation.
Networking / Multiplayer
  • Fast, reliable network implementation using UDP/IP.
  • Solid fault tolerance and hacker resistance.
  • Advanced security measures, including packet encryption.
  • Automatic routing of messages to object controllers.

Core system
  • Resource management with support for pack files and caching.

Pancakes wrote:And where is the benchmark data for common usage?


We haven't posted any benchmark data because there are simply too many different graphics cards supported and too many "common" usage cases.

Pancakes wrote:How about occlusion culling or LOD? What features can I use to optimize performance?


A good way to see the culling and LOD in action is to start a level and then type "wire" in the console. (Open the console using the tilde key, like in Quake.) Close the console (with Escape or Ctrl-W), and walk around to see how geometry is culled by the portal system. The portal system is the single most important performance mechanism for visibility determination, lighting, and shadowing.

Pancakes wrote:I think I've seen on youtube that you've got Phyx support but how do I test out that performance?


The PhysX add-on is a community-maintained plugin that is freely available to licensed users. It is not included in the demo.

Pancakes wrote:So tell me this, and I suppose I can do further testing myself, but as far as armatures and animation is concerned what is the recommended tri count for characters, and complexity for the rig itself before performance will begin to suffer. We have replaced the main character with a 12,000 polygon model for the next version. The important thing is that there are multiple LODs for this model, with 8000 and 4000 polygons at the lower levels. Displaying 4-6 of these is no problem. Complex shaders on characters do not affect performance significantly because they don't cover a lot of screen space, and detailed animations are very cheap.

Re: Why Should I Choose C4 Engine? =)

by jwatte » 01 Jan 2009, 00:16

The editor is slow if you run it with too much geometry in too large a resolution. It's basically the game engine, plus editor widgets, so if you're targeting a GeForce 9800, you shouldn't try to edit on an Intel GMA 950 :-/

The four engines you enumerate are so different it's hard to figure out what you're trying to do.

XNA: This is the only way an unsigned indie can run on the Xbox. If you want to run on the Xbox, you have no choice. However, XNA is simply a fairly thin wrapper around a DirectX-like API; you'll have to add gameplay, scripting, physics and other such functionality yourself. Also, the XNA runtime on the Xbox is really slow on the CPU, because of limitations of the compact CLR. The programming language is C#; practically no other choice. Because you have to do everything yourself, it can be great, but it can also be a lot of work. If you need Xbox support, this is your only choice. Otherwise, unless you really want C#, try something else.

NeoAxis: I never quite understood the benefits of using NA instead of just using Ogre plus your own physics engine. Integrating Ogre, Lua, and something like ODE, Bullet or PhysX isn't all that hard, and gives you a very nice engine. Ogre started out as a little too scene graph centric, and is a bit messy in its API (more messy than the C4 scene graph, for sure), so that would probably be the main drawback. Note that some "bigger names" (like Multiverse) are using Ogre, so it's not likely to die anytime soon. Programming language is C++ for Ogre and the folks; NeoAxis adds a mostly unnecessary layer on top of that.

Blender game engine: This uses python, and it uses Blender. While Python can be okay, especially for high-level stuff, it is not high performance if you want to write 3D processing code. Blender is... blender. I don't like it. The game engine itself isn't all that great, either, in my opinion. I'd put this last on your list.

C4: This is C++ to the core. Apart from the graphical scripting engine, you develop in C++. The C++ API is also very traditional -- there's a class hierarchy with implementation inheritance. It uses virtual functions (including overriding and calling the base), but not much of templates. It is "a way of life" rather than a set of components that you integrate -- if you don't adopt the C4 way of doing things, there will be a lot of little hooks and affordances that you'd want to be there, that aren't. If you live within C4, and can target the kinds of games that it works for, it can be very good.

Another engine you haven't considered, but should:

Panda 3D (from CMU and Disney): This is used in Pirates of the Caribbean, as well as other games. It's fairly mature, and uses python and C++. You _can_ develop in C++, but all the tutorials and quickstarts are in python. If you like Python, this is a pretty good engine; I'd rate it above Blender for sure. If you want something free, run, don't walk, over to the web site and try it out!
