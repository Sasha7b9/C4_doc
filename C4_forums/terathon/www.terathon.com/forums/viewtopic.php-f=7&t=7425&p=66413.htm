Re: RTS on Client-Server model

by david_aiken » 20 May 2009, 22:32

The reason peer-to-peer is popular for RTS is because there is a lot more shared state between players, particularly if you're the sort that amasses a Huge army between raids. In this case the central server has to handle updates for thousands of units, creating a bottleneck. Conventional client/server only scales to about 64 players over the internet (i'm using player/client/peer interchangeably here).. maybe as much as 200-250 for some games (i.e. Planetside on a good day).

Peer-to-peer avoids the bottleneck at the central server, but if each peer has to communicate with every other peer the total traffic scales quadratically. This can be significantly reduced using the same area-of-interest mechanisms used in FPS games i.e. if a unit is in the fog-of-war of a player there is no need to send movement data for that unit to that player. FPS games often handle lag through interpolation and extrapolation, greatly aided by shared code on server and client. RTS games often use a synchronous turn-based approach where each peer exchanges movement information, then runs the same code on the same data in lockstep i.e. http://www.gamasutra.com/features/20010 ... ano_01.htm . I suspect that interpolation/extrapolation simply isn't needed for an RTS since they have less twitch and more strategy than an FPS. Interpolation/extrapolation also gets expensive if there are hundreds or thousands of units to consider.

There are a number of disadvantages to the P2P approach:
- speed of the simulation is limited by the slowest peer so graphics settings and any other settings which affect performance should be adjusted accordingly. This can be a real pain for the other players.
- joining a game in progress requires retrieving state from a peer.. potentially expensive. Multiple peers if each peer has only need-to-know data
- finding other peers to establish a game typically requires special port settings, protocols, and all of the router/firewall (i.e. NAT) issues that come along with them
- certain types of cheats are easier if significant state is on the peer (i.e. remove fog-of-war). This is an active area of research i.e. http://www.computing.edu.au/~webbsd/webb07e.pdf

Some client/server RTS games: USKaarj (UT 2003 mod), Unreal Annihilation (UT 2004 mod) - both, sadly, inactive. Gareth Fouche at GG also discusses a client/server RTS design: http://www.garagegames.com/community/fo ... read/28881 . There's no inherent reason why you can't use client/server to share state for an RTS, but the population limits will be significantly reduced relative to P2P.

Anyway.. take with a grain of salt. I haven't written RTS networking code, though i've played quite a few :>). Hope it helps.

Re: RTS on Client-Server model

by david_aiken » 21 May 2009, 11:13

Glenn Fiedler at http://www.gafferongames.com is pretty good at answering networking questions.

Joining a game in progress is difficult no matter which approach you use if there is a lot of state. You also have to consider the gameplay - adding a new player to a game like Left4Dead is fairly lightweight. If you have 7 players with large armies, and you add in an 8th you not only have to inform the 8th player of all the existing units, you have to give them resources, setup their fog-of-war, etc. and inform all of the other players. And if the game has progressed past a certain point the 8th player is going to have a tough time being competitive (often all of the forests/mines/crystals/... have already been staked out).

Out of curiousity, which Warcraft game do you refer to? The Warcraft II Battle.Net edition allowed up to 8 opponents with up to 1200 units according to http://www.blizzard.com/us/war2bne/, which seems in-line with the Gamasutra article.
