ca$per wrote:Great news! Is there any docs on how to use the water block? And how to use land height data? It seems that whatever maximum wave elevation i enter for water controller it is restored every time i reopen the world and visually has no difference on wave's height. So some small tips or docs would be very welcome.
Apart that, very nice job! Thank you!


Docs and examples are coming shortly. Here are some brief notes:

* Water blocks are drawn like terrain blocks.
* Land height data needs to be explicitly generated for the selected water geometries using the command in the Water page.
* The new Vertex Geometry interpolant in the shader editor gives you access to a three-component value where (x,y) is the normalized land gradient and z is the difference between the water elevation and the land elevation.
* The randomization settings for the water controller don't cause the water to have an initial random state, but just how new random waves are added to the water, so it takes a little time for the overall randomness to build up some energy in the water. We're working on a way to run the wave generators in the editor for a while and save the water in a pre-generated state.

Re: Version 2.6 Alpha Now Available

by TheRhinoDude » 17 Jun 2011, 17:11

Grognard wrote:You probably don't want to do that anyway...


I agree, most C4 games won't need and shouldn't use it. The "lost opportunity" of yanking a core or two from C4's job manager's consideration will almost certainly outweigh the context swiching overhead savings for your typical C4 game.

But our project isn't a typical C4 game.

Jesse Meyer wrote:Isn't Rhino's implied feature request a way of changing 'the engine does its thing' to 'the engine does YOUR thing' ?


Not really. The request is for a simple setting so that you can tell the job manager to simply ignore a certain number of cores from consideration when determining the number of worker threads. The idea is if there is an integrated multithreaded third party library that has similar functionaity, you don't want them both allocating too many runnable threads. This can have significant overhead as the system approaches saturation, and can make the difference between just squeeking by with nearly full backlog queues, and users starting to see timeouts.

As Grognard points out, in most cases you probably don't want to touch this. The default should be as it runs now.


Eric Lengyel wrote:This has not made it in yet, but it should be really easy, so we'll get it into the beta.
