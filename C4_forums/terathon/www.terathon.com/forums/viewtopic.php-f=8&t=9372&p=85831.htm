Yes and that's the technically correct way, it avoids the copy issue I was talking about.

However, a lot of C++ programmers; including myself (and from looking at C4's code, Eric?), like to avoid over-using the initialiser list as things can get out of hand quite quickly. Compilers are usually smart enough to look through the constructor and produce assembler the same as if the assignments were included in the initialiser list. If I find myself initialising 5+ objects I'll move things to the constructor itself and probably make use the heap and pointers for classes/structs and rely on the compiler to optimise basic data type assignments. Another one of those annoying speed vs. maintainability trade-offs.

Then again I wouldn't call this particular example over-use at all, the initialiser list seems spot on.

by Eric Lengyel » 26 Jun 2010, 01:06

Benjamin Dobell wrote:However, a lot of C++ programmers; including myself (and from looking at C4's code, Eric?), like to avoid over-using the initialiser list as things can get out of hand quite quickly.


Here's the rule I follow: If the member has a trivial constructor, then I initialize the member inside the body of the class constructor. This is easier to read, and the trivial constructor generates no code, so no inefficiency is introduced. Otherwise, if the member has a constructor that actually does something, then I initialize the member in the class initializer list.
