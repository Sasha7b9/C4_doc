I've been struggling to find a good workflow for source control and backup for my C4 projects. I generally use Dropbox to backup documents, but I don't want to put my whole solution in Dropbox because it eats up a lot of space for assets that I don't need backed up (eg, the demo assets). I've been using Git for version control, and it makes it really easy to jump between different projects, though I have to be careful to tell Git to delete untracked files so previously built binaries don't hang around after switching branches. Ideally, I'd have Dropbox only backup files that are tracked in Git so that I can just delete demo assets and ignore generated files. Has anyone had luck working on multiple C4 projects using a similar setup?

Re: Source control/backup workflow for C4

by jwatte » 09 Aug 2012, 04:23

Dropbox is in all ways inferior to Git when it comes to syncing a project between machines.
It will "work" as long as you make sure it has time to write all changes from machine A, before you turn that off, and then has time to read all changes onto machine B, after you turn it on, and before you work with it.
As soon as there is a discrepancy, Dropbox does not do conflict resolution that's appropriate for a development project.

In my mind, "git pull" and "git commit; git push" is what defines code as "good enough to keep." If I haven't git committed it yet, then I don't care if the machine dies.
This means I can keep different things going on different machines, and still merge them all together when done (or revert if I change my mind.)
Then, I back up my git repository. This means that I have multiple levels of security:
1) each machine has a clone of the repository
2) the git server has a clone of the repository
3) the offsite automatic backup has a backup of the repository

My remote backup also backs up photos I've taken, MP3s I've ripped from CDs, etc. Note that "backup" is very different from "sync" -- Dropbox is *not* a backup solution, and if you try to use it as such, you will probably run into some case where you regret it later. There are lots of "d'oh!" stories on the web to drive this point home if you search for them.

Note that the C4 engine is commercially licensed, so you cannot use an "open" repository like github or sourceforge or whatever to store your code. You'll have to set up a protected server. I run gitolite on a Linux box in the closet. Your approach may be different, but I highly recommend you set one up somehow!

by Benjamin Dobell » 09 Aug 2012, 07:24

cboyce wrote:Using Dropbox for backup means it's all automatic. I don't have to push every project I have to a remote repo to back it up. Another benefit is that I can keep my workspace in sync across my desktop and laptop (I don't have to push/pull commits just move changes from one compute to another).

You can get plug-ins to IDEs that will auto-commit when-ever you save a file. However, generally speaking it's not a good idea. I really recommend giving Git a go. If you're still thinking of your source code in terms of "backing up" and "syncing" then you're development is not nearly as efficient as it could be. Source control is great for keeping documented history (i.e. why something changed) and allows you to easily revert a whole bunch of files to a known project-wide state. By that I mean you don't revert individual files, doing so will introduce incompatibilities between different versions of files.

Version control is 100% vital when you have multiple people working on a project, but you can also drastically improve your own productivity by taking advantage of it. For instance Git's branching and merging functionality is great for prototyping new features. How often do you start to implement a completely new feature, or drastically refactor and then decide it's too time consuming and just drop what you're working on in order to work on something else? If you use version control all that work is not lost, you can create a branch and come back to that work later when you have more time available. If the two branches diverge, because you've got one branch you've used to refactor, and another which you've added new features to, Git will help you merge the two branches back together when you've finished refactoring.

I mentioned it previously, but I really can't overstate the usefulness of having documented history. Rather than just trying to arbitrarily revert to a week ago, when you know something last worked, you can take a look at the Git history (including your own comments) and work out precisely when things broke, or why certain things were changed. Git blame is also extremely useful, although it's probably more useful when working in a team.

Dropbox is not even remotely a solution. Quite simply, if you're not using version control, you should be!

jwatte wrote:Note that the C4 engine is commercially licensed, so you cannot use an "open" repository like github or sourceforge or whatever to store your code. You'll have to set up a protected server. I run gitolite on a Linux box in the closet. Your approach may be different, but I highly recommend you set one up somehow!

Github do offer paid private repositories. I don't know about Sourceforge. However, at the moment I use Assembla. I used to run my own Git server but it's a lot simpler to let third-party services maintain it for you. Especially since these dedicated services offer much better redundancy than I can afford to setup myself. But more importantly, for large projects anyway, third-party services like Assembla offer integrated bug tracking, team management, document sharing, wikis, planning tools (milestones etc.)

For example:
If you delete an object from a Dropbox folder on one machine, that delete will be "synced" to all other machines.
If you then realize that you actually did want that object, it's too late.
People and companies have lost large amounts of important and valuable information this way.

Also, if you suffer corruption of data files, or need to go back in time and retrieve an earlier version, most backup solutions will have something for you, but Dropbox does not.

There's also the problem of needing to explicitly put what you want to "back up" into the Dropbox folder. A good backup program can back up all your documents and data, wherever it lives. A GREAT backup program even backs up programs and registry and WIndows install, but that's a lot harder to keep versioned and restore

Finally, Dropbox doesn't deal with conflicting edits. When I edit a document in the Documents folder on machine A, and edit that same document in the Documents folder on machine B some other way, then a backup will simply back up each machine separately. Dropbox will "eat" one of the two edits.

Never heard of Dropbox before this, but I use Perforce, and every so often (once every one or two months), I burn the Perforce repo to DVD and move that DVD on my next trip to my storage unit. Sounds pretty antiquated and I guess I'm just waiting for anyone to tell me that I'm doing it all wrong, but it works for me.

I guess the main question would be, what happens when I exceed the DVD size? Well, aside from disc spanning, my repo has just gotten to 1 GB over the past 6 years or so. I've done a few animation projects that were not under "source control" in the past, and that was back when I archived on floppies, zip disks, and CDs.
