The beta build of version 3.5 has been released to all users. Updated release notes can be found here:

http://www.terathon.com/wiki/index.php/ ... ersion_3.5

This release includes a fully functional OpenGEX exporter for 3D Studio Max. The file "OpenGex.dle" is a pre-built binary for Max 2014 that can be copied into the Max plugins directory. After this release, OpenGEX exporters will be made available on the opengex.org website instead of being included with C4 releases.

Re: Version 3.5 Beta Now Available

by Eric Lengyel » 14 Dec 2013, 00:08

Jesse Meyer wrote:I'm really excited seeing Radiosity beginning to sneak into the code base. Thanks for the hard work, Eric!


This will actually be in 3.5 final. (It's not available in the beta.) There's a new radiosity space that stores indirect lighting intensity for six directions at each sample point on a 3D grid. The data is generated by simply rendering the scene at each point and capturing the amount of direct light that can be seen reflected from all the geometry in view for each direction. Previously generated data can be fed back into the process to iteratively refine the data, resulting in a final 3D texture that stores true radiosity and can be used as a volumetric light map. Just like the existing ambient space, dynamic objects moving through a radiosity space pick up the lighting as well (but don't affect the data itself).

Re: Version 3.5 Beta Now Available

by Eric Lengyel » 15 Dec 2013, 15:59

Benjamin Dobell wrote:It seems that you've setup the Max exporter to by default write floats as hexadecimal literals rather than as float literals. Sure hexadecimal helps with the alignment, but given that human readability was a key design goal for the language; wouldn't the more human-readable float literal representation be more suitable?


The problem with decimal literals is that they lose precision when you convert to and from the binary representation. Hex floats are written in the OpenGEX file for most things (but not all) so that the transforms and vertex data are reproduced exactly by an importer. In a lot of cases, the exporter writes the decimal equivalent in a comment next to the hex floats so that you can read the values easily. Since you have the source for the exporter, you could always change it to write decimal for everything if you wanted -- it's a trivial modification.
