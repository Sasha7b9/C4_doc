Fratercide wrote:Looking great!

CodeNewt wrote:Looks really professional, looks amazing!

Thank you so much >v< its really motivates me.

Botagar wrote:nice.
How are you doing the pathfinding? That method which has something to do with city block squares to iteratively calculate the shortest distance (gawd i cant remember what its called...)?

City Hmm...blocks...I guess your referring to the Manhattan distance heuristic. Yea this is the default heuristic I'm using, the other 2 standard ones are diagonal and Euclidean distance. Manhattan is really quick as it only take into account 4 directions, since I'm using 8 way grid I have to smooth the path, turns out to be much quicker than the other 2 as their path need to be smoothed as well anyway. Heuristics is what makes A* algorithm so fast. Heres a good website about heuristics http://theory.stanford.edu/~amitp/GameP ... stics.html

Basics A* is quite straight forward to implement, once that is done you can start optimize and extend it.

I'm using A* algorithm with mahattan heuristic, binaryheap for openlist, hashmap for closed list, 8way grid only nodes no edge, and everything uses a memory pool (no new and delete). I "time-sliced" A* so it runs across multiple frames. Uses 2 path smoothingpass. First pass I use the Funnel algorithm http://digestingduck.blogspot.com/2010/ ... rithm.html , second pass I iteratively do straight line ray cast to points along the "rough" path. All paths are recalculated in regular intervals (default 500ms). I use breadth-first search (BFS) to find the closes valid nodes.

Depending on your needs, it doesn't need to be this complicated. I have to move lots of units in real time though!

Re: RTS project

by Grognard » 20 Aug 2011, 04:46

If you call pathfinding within Move() or a timed job then the main thread is always running.

I tried and failed to explain this before in some of my change requests, but here is what will happen.

1. engine stuff for this frame.

LOOP
2. main thread calls timed jobs or move, request fired.
3. Main thread waits on job.
END LOOP

So if you just call it like that then you actually go slower because you are contexting out the main thread to run a single job, possibly over and over for each unit.

I ended up using my own job queue that's asynchronous, but you could also do something like collect all the requests and execute them all at once every thread.

But ideally you DON'T want to leave your frame update hanging on pathfinding requests, ever. So you need to have another thread running to really make this work right, or else have a job manager that isn't lockstepped to the frame execution. But effectively speaking, having extra threads running is not as big of a deal as it sounds like. It only matters when you context out the main thread, which is going to happen any time you call on wait, which unfortunately the job manager also does. But even so a small number of extra threads should be ok so long as they yield between jobs.

by Grognard » 01 Sep 2011, 17:35

yaure wrote:Have you implement pathfinding with your job queue? if so have you time slice/load balance it? Hows performance?


For my game I need to have a visible path update as you move the mouse around, much like Jagged Alliance or Silent Storm. I have it constantly update the path in the background. The updating checks every frame if there is a new result so it never blocks and there would be zero waiting.

For AI it is the same situation. A whole game turn of AI gets calculated at once but the AI is able to use the done parts before they whole round is calculated. If there is an interrupt or something then it invalidates the turn from that point on and it picks up seamlessly from there.

But the performance of the actual A* is very good anyway, and it's done in a very easy to use, generalized manner. At some point I will release at least the basic part of the A* code to the public.
