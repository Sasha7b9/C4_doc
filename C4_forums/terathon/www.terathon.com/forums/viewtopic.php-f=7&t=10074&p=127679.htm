by Twisted Helix » 14 Dec 2010, 22:19

Putting a break point next to Application::HandlePlayerEvent() in the Game::HandlePlayerEvent() code, does it trigger ?

If not it suggests that your Game class has not been correctly constructed somehow.

If it does then you need to find what the actual message being transmitted is because it would seem its not kPlayerChatReceived.

One possible and likely problem therefore could be that you are not actually constructing the message in your Game class. When the network message is recieved it is first handled by a Message construction method, which recognizes the type of message passed (from its serialized network transmitted form) and then returns a new message of the type you want to handle. This message is then handled by your HandlePlayerEvent() method. I would hazard a guess that you have not included the code to construct the message and that some default message is getting created and this is triggering the Application method because there is no case to handle it in the Game method.

http://www.terathon.com/c4engine/doco/S ... ssage.html

Also the application HandlePlayerEvent is triggered by a number of basic messages such as connect, disconnect and basic initialization and synchronization.

by CodeNewt » 16 Dec 2010, 16:56

The only thing that changed is the you have to register the commands differently using a CommandObserver object.

This is done by declaring the object in your project
Code: Select all
CommandObserver<Game> coolObserver;
Command coolCommand;

And registering it to the game class with
Code: Select all
void Game::Game() : coolObserver(this, &funcToHandleCommand), coolCommand("cool", &coolObserver)
{
    TheEngine->AddCommand(coolCommand);
}

void Game::funcToHandleCommand(Command *com, const char *text)
{
    Engine::Report("Cool stuff.");
}


Other than that, it is exactly as it should be.
