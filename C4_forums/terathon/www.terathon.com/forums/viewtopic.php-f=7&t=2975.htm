by Optime » 08 Aug 2007, 13:00

I don't know if anything frame based is a good idea. From NTP:

Synchronizing a client to a network server consists of several packet exchanges where each exchange is a pair of request and reply. When sending out a request, the client stores its own time (originate timestamp) into the packet being sent. When a server receives such a packet, it will in turn store its own time (receive timestamp) into the packet, and the packet will be returned after putting a transmit timestamp into the packet. When receiving the reply, the receiver will once more log its own receipt time to estimate the travelling time of the packet. The travelling time (delay) is estimated to be half of "the total delay minus remote processing time", assuming symmetrical delays.

I found another algo that does averaging:

....
(So far this algothim is very similar to SNTP)
4. The first result should immediately be used to update the clock since it will get the local clock into at least the right ballpark (at least the right timezone!)
5. The client repeats steps 1 through 3 five or more times, pausing a few seconds each time. Other traffic may be allowed in the interim, but should be minimized for best results
6. The results of the packet receipts are accumulated and sorted in lowest-latency to highest-latency order. The median latency is determined by picking the mid-point sample from this ordered list.
7. All samples above approximately 1 standard-deviation from the median are discarded and the remaining samples are averaged using an arithmetic mean.

by Ludi » 10 Aug 2007, 11:04

Okay, seems like there's a little bit of misunderstaning. The server doesn't know how much the clients are off.

When a new server starts, he starts an internal timer, the "network time". All clients, which connect to the server are syncing their "network time" with the time of the server by polling updates.

The idea behind that is the following: When a player shoots, he sends message to the server, the server acks that with the "network time" (let's say 12000) and sends it to all the clients. Now, when this message arrives at the a client, the client can calculate the delta time (if it arrives at 12200, we have a delta of 200). How with this delta, the start point and the velocity, the client can put the projectile at the correct position (startpoint + delta*velocity).

This is completly different from how the game demo works, but it should give a much smoother gameplay (at least for shooting projectile weapons ).

And there are lots of other things, which can be done, when you have a global "network time".

Polling from the server isn't the best way to test.

I would assume that getting an atomic clock interface for each computer, and writing something that logs the game time calculated at regular atomic clock time intervals would be a better test. That way, you have a very accurate baseline (atomic clock) and can compare what the different machines thought at the same time.

Beware, though, that if you're getting a radio-based atomic clock interface, it needs to be calibrated for the distance between the time sender station and your location, as the speed of light (or in this case, radio waves) actually matters.
