Re: ZBrush into C4?

by Jesse Meyer » 16 Jan 2014, 23:35

If Zbrush exports to the Collada format then the pipeline isn't generally any different from Maya or Max. Remember to export a polygonal mesh that contains less than 65536 vertices, which may be problematic for high resolution sculpts, but that's easily solvable by baking height or normal maps and importing those too along side a low poly version of the sculpt. Since there are a few different common use case I cannot detail the precise procedure.

Since ZBrush can export to Maya format, the best way to get ZBrush art into C4 would be to transfer it to Maya and use the OpenGEX export plugin for Maya, which will be released early next week, to create a file that C4 can read. See http://opengex.org/ for more information about OpenGEX.

Hi gogo!

You retopologize your Zbrush models, right? Because the retopology should be what you import into C4, not the direct Zbrush sculpt itself. I use Blender, but the pipeline for Max and Maya wouldn't be too different. I create a model in Zbrush, retopologize it in Topogun, set up the UVs for the new topology in Blender, then feed everything into xNormal and bake my maps there.

ropollock wrote:Would it be possible to get a standalone tool to convert say an obj, or .ma to openGEX?


Maybe. A converter for .obj might be especially easy to write, but it wouldn't support many of the features of OpenGEX. A converter for .ma would be much more difficult. At the present time, we will have to leave it to other people to write either of these utilities.

Thinking it could be a path resolution issue. Look in your Maya.evn file and see where the plugins and module path variables are pointing. Here's an Autodesk guide regarding them:

http://download.autodesk.com/global/docs/maya2014/en_us/index.html?url=files/Environment_Variables_File_path_variables.htm,topicNumber=d30e137272

Being on an academic network might require you to consult your network/lab admin if the settings, license and other Autodesk related stuff is pulled from a server location/is not local to the machine.

Furthermore, as the link to a related issue below indicates, version of the modules you are trying to load must match what's in the Maya.env file, if there are separate entries/old info present:
https://support.solidangle.com/pages/viewpage.action?pageId=7503891

Hope this puts you on the right track. Thankfully it doesn't seem to be an issue with the plugin itself. Just Maya and its quirky ways of parsing plugins and settings.

by eborenst » 30 Jan 2014, 18:09

I may be off on this, but I think I know what's happening (and I was getting the same error as you but have now resolved it). According to the Maya 2014 docs (http://docs.autodesk.com/MAYAUL/2014/EN ... r=d30e4403) plugins are expected to be built using Visual Studio 2010. I know I've seen issues in older versions of Maya when compiling plugins with an unexpected version of VS. From the OpenGEX page, it looks like the plugin in the zip was built using VS2013.

I only have VS 2010 on my machine, so I found that installing the VS2013 redistributable (https://www.microsoft.com/en-us/downloa ... x?id=40784) fixed the issue for me.
