Build 122 now available

by Eric Lengyel » 24 May 2006, 20:32

Build 122 is now available at the registered developer download site:

https://www.terathon.com/developer/download.php

This is the first release of the Blade series. At least one minor update in this series will follow (next week). Release notes are here:

http://www.terathon.com/developer/notes.php

There are a few things that will be completed in next week's update:

1) There are slots for two diffuse texture maps in the material editor. If both are specified, then the second one is currently ignored.

2) There are settings for texture coordinate scale in the material editor. These are currently ignored.

3) Motion blur will currently work only if FBOs are supported (which means Nvidia hardware on Windows). A p-buffer fallback will be implemented in the minor update.

Although multiple texture coordinates are supported in the rendering code, there's no way to generate them in the editor or to import them yet. (However, it's possible to generate them through animation.) The Collada 1.4 update in the Cannon release will provide this functionality.

Re: Build 122 now available (multiple texture coords)

by Eric Lengyel » 25 May 2006, 00:59

Huidafa wrote:Is it something like a second TEXCOORD semantic (perhaps TEXCOORD2?), interleaved with the TEXCOORD semantic? Can you provide a brief Collada stream excerpt to show how it's formatted? I didn't see anything obvious in the schema for this.


Here's an example I found in the Collada 1.4 spec:

Code: Select all
<mesh>
  <source name="grid-Position"/>
  <source name="grid-0-Normal"/>
  <source name="texCoords1"/>
  <source name="grid-texTangents1"/>
  <source name="texCoords2"/>
  <source name="grid-texTangents2"/>
  <vertices id="grid-Verts">
    <input semantic="POSITION" source="#grid-Position"/>
  <vertices>
  <polygons count="1" material="#Bricks">
    <input semantic="VERTEX" source="#grid-Verts" offset="0"/>
    <input semantic="NORMAL" source="#grid-Normal" offset="1"/>
    <input semantic="TEXCOORD" source="#texCoords1" offset="2" set="0"/>
    <input semantic="TEXCOORD" source="#texCoords2" offset="2" set="1"/>
    <input semantic="TEXTANGENT" source="#texTangents1" offset="2" set="0"/>
    <input semantic="TEXTANGENT" source="#texTangents2" offset="2" set="1"/>
    <p>0 0 0 2 1 1 3 2 2 1 3 3</p>
  </polygons>
</mesh>


It looks like you just reuse the TEXCOORD semantic, but specify the "set" attribute to differentiate between the two arrays.

Huidafa wrote:Once there are two sets of UVs, can you control the weighting between the two textures or is it fixed at a 50/50 mix?


You can add, blend with the alpha channel from either texture, or blend with the alpha channel from a color array. There may be more modes added to this.

Huidafa wrote:Finally, could this feature be used as a poor man's multiple textures on a mesh (well at least two of 'em) to superimpose a smaller unique texture onto a larger one that is used many times at runtime or in the world editor?


Sure. You could either assign a separate material to each instance, or leave only one texture in the material and assign a second texture using the auxiliary material attribute list.

by 0x336699 » 25 May 2006, 01:17

Implemented delta save files for saved games. Saved games get stored in the Save/sav/ directory. (The Save directory is the root of a new resource catalog.) Games are saved and restored using the WorldMgr::SaveDeltaWorld() and WorldMgr::RestoreDeltaWorld() functions. A save game file stores the entire node hierarchy and all controller information, but it only stores the objects that it actually needs to store.


Wow. None of the other engines I've looked at ever even come close to addressing the problem of saving games. (Which has always amazed me.) I'm very impressed that you take the time to write boring-but-important features like this in addition to more glamorous things like fancy motion blur post-processing effects and realistic water.
