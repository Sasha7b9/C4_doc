Re: A few Questions before I order C4 Engine

by Eric Lengyel » 10 May 2012, 14:55

gameengineer wrote:Is the shader version controllable?


When using C4, you don't access the shader version directly. The engine handles the tasks of compiling your shaders correctly for whatever GPU happens to be in the computer.

gameengineer wrote:What is the minimum shader model required for target machines?


SM 3.0 / DX9 hardware.

gameengineer wrote:Can C4 work with lower end video cards (eg. SM 2.0)?


C4 used to support SM 2.0 hardware, but that was removed in 2005. You're talking about antique GPUs.

gameengineer wrote:Are there near term plans to allow for completely custom made shaders written in Cg, HLSL or GLSL? (this question stems from a lack of understanding on what the C4 Shader editor can do)


No. And you wouldn't want to write directly in GLSL if you wanted to support a lot of different GPUs. The engine takes shaders you've made in the shader editor and generates the correct GLSL code for the capabilities of the GPU in the machine running C4. If you wrote GLSL directly, you'd have to write several different versions of every single shader.

gameengineer wrote:In the particle editor how much customization do we have if some attribute we wanted was missing? For example (and I haven't check too closely yet...) if particle scaling over time was not available is it possible to add this to particles?


You have full control over any imaginable particle attribute through C++ code.

gameengineer wrote:Does or can the engine use shadow mapping for increased performance? (I got this answered in another thread. ans. shaders can be easily used for lightmapping)


The engine supports shadow mapping in addition to stencil shadows (but shadow mapping isn't always faster). Shadow mapping is not the same as light mapping. You can generate light maps in external tools and apply them as textures in the shader editor if you want. This would only be useful for things like medium-scale baked ambient occlusion. We use it on several of our models.

gameengineer wrote:How much control over the dynamic shadows and lighting do we have? Can I lower shadow quality to increase performance?


The engine contains built-in settings for dynamic light and shadow level of detail. Basically, you'd want some dynamic lights to not be rendered on low-end systems, and you'd want the shadow map resolution to be lower.

gameengineer wrote:Is frustum culling done?


Frustum culling is the simplest of a large set of complex scene culling methods used by the engine. All engines have frustum culling.

gameengineer wrote:If the world editor is not sufficient can we create a terrain externally, export to a supported file format (Collada), incorporate it and have object collisions work?


Yes.

gameengineer wrote:Is there good documentation for creating custom plug-ins?


Yes, the API documentation covers this.

gameengineer wrote:Is there an update to “The Beginners Guide to the C4 Engine” document?


The authors are currently working on an update.

gameengineer wrote:Is a splash screen required for the Standard Version commercial releases? We have no problem giving credit by showing the splash screen we just want control over when its shown.


The splash screen is not required, but you do need to show some kind of C4 logo otherwise. You have full control over when either is shown.

gameengineer wrote:Is there support for Steam? I believe Steam has a C++ interface for apps so this may be fine.


Yes.

gameengineer wrote:The demos have an in-game menu system with dialogs etc. Do we have custom control over doing our own GUI?


Yes, there is a complete GUI editor included with the engine:

http://www.terathon.com/wiki/index.php/Panel_Editor

Re: A few Questions before I order C4 Engine

by Eric Lengyel » 11 May 2012, 01:53

It looks like C4 would still support some SM 2.0 hardware. It was SM 1.4 support that got removed in 2005. (The was no OpenGL correspondence with shader models back then.)

C4 runs on a GeForce FX 5xxx or later from Nvidia, which goes back a little more than 10 years. Nvidia no longer supports GPUs this old, and no new driver updates will ever be available for them.

C4 also runs on Radeon X hardware from ATI, which also goes back 10 years. These GPUs do not support PCF (percentage closer filtering), so shadow mapping won't look right. These GPUs are also no longer supported by AMD, and the drivers are not being updated.

Re: A few Questions before I order C4 Engine

by Eric Lengyel » 06 Jun 2012, 14:04

The voxel technology in C4 is primarily meant for static terrain, although it is possible to employ the same methods used in the editor to change terrain dynamically in a game. The voxel terrain is stored in a coarse octree that also incorporates level-of-detail, and the C4 Engine is where the Transvoxel Algorithm for seamlessly stitching together different LODs was invented.

The engine does not support cubic voxel meshes, but it would be a lot easier to create such a mesh based on the raw voxel data.

There is also voxel support for blobby particle systems, if that interests you.

Re: A few Questions before I order C4 Engine

by Eric Lengyel » 06 Jun 2012, 22:58

DefiniteIntegral wrote:In regard to threading, I am more interested to know whether C4 is already thread safe for arbitrary API calls.


Only very limited parts, such as the memory manager, of the C4 API are thread safe. This is the case mainly for performance reasons -- it's a game engine after all, and we don't want to spend a significant amount of time acquiring mutexes for every call.

The C4 Engine contains a full set of cross-platform multi-threading tools and synchronization objects. In particular, there is a job manager that can be used to efficiently distribute work to all cores available on a machine. You can find API documentation for this functionality here:

http://www.terathon.com/c4engine/doco/System/index.html

by Eric Lengyel » 06 Jun 2012, 23:55

DefiniteIntegral wrote:I died repeatedly, it certainly is difficult. Very well done.


Thanks. You can type "god" in the console if you want to cheat.

DefiniteIntegral wrote:The only thing that really concerns me is the referenced object implementation requiring shared objects to inherit from a base class, and shared pointers using a custom implementation.


The Shared base class really isn't used very often, and you'll hardly notice it in day-to-day coding for C4. It's main use is reference-counted "object" subclasses that can be shared by multiple nodes in the scene graph (for example, so many instances of a geometry node can share the same vertex and triangle data stored in a geometry object). For these objects, you would simply call the Release() member function instead of using the delete operator to relinquish your ownership of them. The AutoRelease class is just a convenience, and it's use is never required.

In order to avoid cross-platform inconsistencies and compiler compatibility problems, we do not use the standard C/C++ libraries at all. You would be free to use std::shared_ptr with your own code, but you wouldn't be able to use it with any C4 objects in place of the Retain() and Release() functions.

Re: A few Questions before I order C4 Engine

by Eric Lengyel » 07 Jun 2012, 00:20

DefiniteIntegral wrote:Wow, C4 is entirely written in core C++99?


Yes, it doesn't even link against STL or anything when it's built. Over many years, I've found this route to be the most sane for a cross-platform engine, given that different implementations of standard library functions can be buggy or have different performance characteristics. Code that works great on one platform could break or be quirky on another just because the library functions aren't identical. When we're running nothing but our own code, moving to a new platform is much easier. We recently moved to the Linux platform, and we didn't have to change a single line of game code. Everything just worked.
