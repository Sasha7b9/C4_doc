Re: Onscreen Clickable GUI

by Eric Lengyel » 10 Jun 2009, 18:06

For games that have an interface of some kind constantly accessible to the user, I don't recommend letting the input manager change modes. You can disable the automatic mode switching by making the following call:

Code: Select all
TheInterfaceMgr->SetInputManagementMode(kInputManagementManual);


Then, I recommend disabling the raw input from the input manager as follows:

Code: Select all
TheInputMgr->SetInputMode(kInputInactive);


When you do this, the windows you have on screen will always be able to receive input, but to get gameplay input, you'll need to go through the standard mouse and keyboard event handlers. You can install your own handlers using the following classes:

MouseEventHandler

KeyboardEventHandler

(In version 1.6, a small change has been made to the keyboard event handler. It's HandlerProc will need to return a boolean value indicating whether the event was handled successfully.)

Re: Onscreen Clickable GUI

by Eric Lengyel » 10 Jun 2009, 19:35

MattF wrote:That does help somewhat. However, if I'm in mouselook mode, I don't want the GUI elements to be able to receive input. Is there a way to tell the entire GUI to, uh, well.. how do I put this -- sit down and shut up? Or when in game input mode, does the interface essentially ignore cursor position while MouseDeltaX/Y are being used?


There are two modes of input for the mouse:

1) Ordinary mouse input with a screen cursor for which the mouse event handlers are called.
2) Input manager raw mouse input where you only get deltas and button events. There is no cursor (and consequently, no cursor position).

The input manager raw mouse input is active when the current input mode includes the kInputMouseActive flag. Otherwise, the ordinary cursor-based mouse input is active. You can only get one of these at any time. By default, the interface manager switches between modes automatically based on whether any windows capable of receiving input are currently on the screen.

Also, just wanted to toss a quick thanks to you for making such a brilliant engine. It has, by far, the most concise and organized code I have ever seen.

Our final method was to create an onscreen gui (inherits from interface) that would return whether you clicked on it or not. When you clicked it would do an Interface->FindElement(Point3D mousePosition) and if it didn't come back null, we'd say that it was dealt with by the game interface and should be ignored for ray-casting purposes.

If you wish to disable it during mouse-look, you could also call Close() on the interface and Open() when it's possible to click on it again. Another idea would be to just make the mouse set to the middle of the screen, hide it, and each time you move, use the mouse delta to modify the camera angle.

by Eric Lengyel » 08 Jul 2009, 20:39

ropollock wrote:How can I make it so that the tools menu and the command prompt work correctly?


You'll have to make the keyboard inactive in the input manager in order to use the keyboard for the command console or to use any shortcut keys. You can change the keyboard back to active whenever you want to receive action events for the keyboard.

You can hide the menu bar and close the command console in code with the following function calls:

Code: Select all
TheInterfaceMgr->GetMenuBar()->Hide();
TheConsoleWindow->Close();

Re: Onscreen Clickable GUI

by ropollock » 29 Jul 2009, 08:44

Alright for those wanting to do override the console because their game requires manual input management, you need to create an action that:

1. Is bound to something other than tilde

2. Sets InputKeyboardActive

3. Shows the console window and sets the console window as the active window

Then a keyboard listener must be installed for your application that:

1. Listens for whatever key you bound your action as earlier

2. Sets & ~InputKeyboardActive

3. Hides the console window

Lastly to disable the console window setup by the engine, in the input.cfg add a line that says:

unbind "`";

(You may have to add more unbind statements if multiple language support is needed.)

That will remove the action bind for the console window that the engine creates on its own.

If you do these steps then you have effectively overridden the default console window.
