No, I'm not really concerned about technical issues like those. It's more about the amount of work that would be necessary to get the engine to transmit synchronization data about certain types of objects that were designed to be run independently (at some level) on multiple machines, like cloth, rope, particle systems, and rigid bodies like body parts from an exploding character that don't interact with "live" objects.


Ah, if I were to implement a general clustered rendering solution *within* the scene graph, then I wouldn't allow the slaves to run some of the objects (e.g., cloth) independently - I would strictly send each and every change in the master's scene graph (transformation changes, vertex position changes, everything) to the slaves.
If the complete state of an object is recorded in a set of fields in a scene graph node (think VRML), and those fields are "intelligent" in that they automatically put changes into a change list, then that list can be sent to all the slaves, and they just apply those changes to their nodes and fields.

However, I was not asking about a general solution *within* the scene graph. I was asking about a special solution that sits on top of C4 and that we would implement (if we deice to use C4).

Re: Stereo Rendering?

by Eric Lengyel » 02 Dec 2013, 17:55

gogo wrote:1) It seems (at least as I had it configured) the whole screen doesn't show up in the Rift. I can't, for example, read any of the stats along the top of the view, or the notifications at the right. I'll need to play with the display settings a bit to see if I can make it better.


It's all there, but the edges of the screen are far off into the periphery, so you can't really see them. Take the lenses out of the Rift and look directly at the LCD screen, and you can see everything. The HUD in the game code has not been updated for Rift at this time, but we'll eventually have to pull all the widgets in toward the center of the full display so they are visible.

gogo wrote:2) When the engine starts up, there is a default "forward" that seems to be set when the game first launches. This means you have to be careful how the Rift is oriented at start up. A "re-home" button/function might be a good idea.


It shouldn't matter how the Rift is oriented at startup. The engine does not store an initial forward direction. The only modification to the game code was that the absolute Rift orientation was added on top of the mouse orientation.

gogo wrote:4) Accessing the menus is very difficult when you are inside the Rift. Again, this probably has to do with the display settings on our system.


This is not due to your display settings, but to the fact that the GUI in the game code has not been redesigned for Rift at this time. The desktop is positioned at a very close depth.

gogo wrote:5) The reticle only shows up in one eye (I think). This makes aiming...interesting. What is the "right" behavior?


The reticle has not been updated for Rift at this time. The game code shoots straight forward as defined by the mouse input, and the additional Rift orientation is only a head look. The reticle is still drawn in the exact middle of the screen, though, so it's not accurate unless you're looking directly forward.

gogo wrote:6) I definitely started feeling woozy after a couple of minutes. I have the Rift latency tester I'll throw on the device to see what the latency is.


Since the engine is currently rendering the whole scene twice (along with shadow maps, etc.) in this preliminary build, I'm sure the latency is terrible.

gogo wrote:7) Having a disembodied weapon is strange. Where's my arm?!!?! I can see it/me in the shadow.


The player model is not rendered in the first person view in order to avoid near-plane clipping. The game code will be updated for Rift at some point in the future, and we'll do something about the floating weapon.
