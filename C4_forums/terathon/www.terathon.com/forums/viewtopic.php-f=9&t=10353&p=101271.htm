Re: Panel editor widgets

by Eric Lengyel » 14 Feb 2011, 23:34

There is no distinction between widgets used in general GUIs and the in-game panel effects. Unifying these systems was one of the main goals of version 2.5. We'll be adding a bunch of panel controller functions so that all of the widget types can be modified from a script. You can also create and register custom Function classes similar to those in C4Panels.cpp to manipulate the new widget types.

Re: Panel editor widgets

by jimbobjames » 16 Feb 2011, 02:16

Robert wrote:Is a completely editor-made panel loadable, displayable and accessable as GUI element, from within both code and script now ?


Here's an example of how to use that Load() function. You can add code like this to (say) SimpleBall (eg at the end of the GameWorld::Preprocess() function, just before the line "return (kWorldOkay);"
Code: Select all
if (TheInterfaceMgr != nullptr) {
QuadWidget *myWidget = new QuadWidget(Vector2D(TheDisplayMgr->GetDisplayWidth(), TheDisplayMgr->GetDisplayHeight()), K::white);
myWidget->SetWidgetPosition(Point3D(0.0f,0.0f,0.0f));
myWidget->SetWidgetAlpha(0.0F);
myWidget->Load("../Tutorial/world/TestPanel");
TheInterfaceMgr->AddWidget(myWidget);
}

The above assumes your test panel ("TestPanel.pan") is saved under the folder Data/Tutorial/world. It will create a transparent widget and places your panel on top of it.

Thats because of how the virtual directories work, you can't access any physical files in the root directory "Data/" because the engine starts looking inside the subdirectories "Data/C4", "Data/Blah", "Data/Demo", etc first.
So if you load "test.pan", it will look for "Data/<doesn't matter what this folder's name is>/test.pan", the first one that is found is the one that is used.

http://www.terathon.com/wiki/index.php/ ... irectories
All resources are stored inside the Data folder, where resources can be organized in an arbitrary manner. However, the top-level contents of the Data folder have special meanings.

All of the top-level sub-folders of the Data folder behave as if their contents belonged to a single virtual folder at the root of the resource name space. These top-level sub-folders exist only for external organization and do not participate in the unique identification of any resources.

Just to add to an already good thread... if you want to purge your UI and replace it with another one, you need to remember to call preprocess on it if you are doing things in the preprocess step like pulling out references to widgets:

For instance, in my main menu, if a user starts off in 4:3 and switches graphics modes to widescreen, I dump my main menu panel and load a new one that is better suited to 16:10. After I do that, I have to call preprocess to get my references back for the new widgets:

Code: Select all
PurgeSubtree();
Load("WF4UIMainMenu/WF4UIMainMenuWidescreen");
Preprocess();


Code: Select all
void WF4UIMainMenu::Preprocess(void)
{
   GameWindow::Preprocess();
   
   okayButton = static_cast<PushButtonWidget *>(FindWidget("MM_OK"));
   background = static_cast<ImageWidget *>(FindWidget("MM_Background"));
   redArrow = static_cast<ImageWidget *>(FindWidget("MM_RedArrow"));
   blueArrow = static_cast<ImageWidget *>(FindWidget("MM_BlueArrow"));
   scratchBackground = static_cast<ImageWidget *>(FindWidget("MM_ScratchBG"));

Re: Panel editor widgets

by Eric Lengyel » 11 Sep 2011, 14:51

There's no way to automatically force a widget to stay on top of everything else. An ugly hack that you could use to keep the widget on top whenever another window is created would be to make this call:

Code: Select all
widget->GetSuperNode()->AddSubnode(widget);


Also, the panel editor does not have a function to load separate panels into another panel.

Re: Panel editor widgets

by Eric Lengyel » 12 Sep 2011, 12:24

It looks like you're getting a nullptr returned from GetBoundingBox(). This can happen if your widget hasn't been updated yet, which would be the case if you add a widget to the system from inside a Move() function. Check the return value of GetBoundingBox() for nullptr before using it.

Concerning the widget-always-stays-on-top-stuff, i have found the function AddSubwindow(new Widget) to work fine for my purpose. This keeps it on top as it seems, and in this case it's even somewhat practical that the parent is inactive as long as the child stays alive, and i don't have to change parent windws yet so the hack is not yet necessary.
The only headache it gave me at first was that the Subwindow also gets the transform of the mother window, until i recognized what that actualy meant for the child : the coordinates for placement were also in 800x600, the size of the parent widget. Not in Screen size. Which of course turned out to make it much easier to calculate the wanted position.
After that i just scaled the child down by a bit, translated it to fit the middle of the screen, and TADA ! There goes the chat window that doesn't vanish when clicking the background.
Once one gets the hang of how a few things work, sometimes with some help, C4's GUI capabilities are throughoutly impressive and stunningly logical.
