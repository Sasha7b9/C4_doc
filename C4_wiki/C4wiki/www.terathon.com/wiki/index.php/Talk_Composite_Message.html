Talk:Composite Message

From C4 Engine Wiki

Jump to: navigation, search

Thanks Cthulhu, for taking the time to carefully document and share your proposed messaging system.

Now that you have posted your work here on the Wiki where it is more likely to be found and used by other C4 Engine licensees, the time was ripe to provide an analysis of this proposed "composite" messaging system, to provide some constructive criticism, and to offer a proposal for an alternative implementation that provides the same benefits and more, without the inherent problems that await unwitting novice programmers who might make use of your proposal.

My Two Cents

More advanced programmers can decide for themselves, but I urge novice programmers to shy away from this proposed messaging system in its present form. Despite this system's alluring "compactness", in practice, the results will be far from optimal, and novices likely won't discover the hidden problems until they have already invested a lot of time and effort into switching over to this system, after which it will be very expensive to go back.

I've been down this road on other projects, and the tradeoffs made by this system don't work in practice, primarily because some of the programming practices used in this system are seriously error prone.


Hidden problems

For example, once program execution has left the local scope where one of these composite messages was assembled, and the message has been decompressed from the network transport stream as applicable, how does one inspect the values of the assembled composite message from within the debugger, before it is disassembled by the receiver? (In a large node and controller hierarchy, it is not uncommon to find oneself debugging a problem that requires inspecting a message right after it is decompressed, before the message is delivered to its final addressees, or acted upon in some other way.)

Once a message in the proposed system is decompressed from the network transport stream, it's still an anonymous tree of values until a knowledgeable receiver (more about that in a moment) disassembles the message back into semantically meaningful parts. Until that happens, even if one is willing to try and decipher the composite message tree contents, the semantics of the individual message parameter values are lost.

And for a messaging system that purports to be more elegant, it throws away compile-time safety for message parameter value types, requiring the programmer to very carefully re-declare message parameter types on the receiving side. When using this proposed messaging system, if one should accidentally mismatch the types on either side - watch out for strange behaviors and difficult-to-diagnose crashes!


A Proven System

In contrast, the existing C4 Engine message system allows the compiler to automatically use the declared type of each message member variable, so that the programmer need only be concerned with streaming the message parameters in consistent order (which the proposed message system also requires). This point is crucial - the shared declaration of each message parameter type in the C4 Engine messaging system enforces that the sender and receiver are using the same types for each message parameter value.

Furthermore, once a message using the C4 Engine message system is decompressed, anyone, including the debugger, has the ability to inspect its contents with the semantics offered by its shared message class declaration.


A Point of Agreement

I'm not proposing that the C4 Engine messaging system is perfect, and as an engineer who has implemented hundreds of message classes using the C4 Engine APIs over the last two years, I agree with the sentiment that there is too much surface area for each message implementation.


Constructive Criticism

Now given the amount of effort Cthulhu has taken to devise, document, and share his proposed system, it wouldn't be right to simply criticize it without having a proposal for something better.

As an alternative to the proposed "composite" system, one could implement a much more reliable and elegant system using key/value/type triplets, with default values for optional message parameters, that would provide compile-time type safety, and allow both the sender and receiver to set and get message parameters using random access.

Such a system would also properly encapsulate the message assembly and disassembly in a shared base message class, instead of in the object to which the message is addressed, and the parameter streaming code would be fully automatic and hidden away in a shared base class.

Most importantly, using key/value/type triplets for parameters would maintain full semantics for both the sender and receiver at all times, and such triplets could also be interpreted in the debugger without trying to tediously match up the ordinality of anonymous array entries against their semantic counterparts.


Summary

Thanks again to Cthulhu for taking the time to carefully document and share his proposed messaging system, but until a superior messaging system implementation is available, I recommend sticking with the existing message classes provided by the C4 Engine.
